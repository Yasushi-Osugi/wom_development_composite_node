# Phase 8-3c-3 Request Letter — 案4 を測る／在庫が損益に効いていない件を確かめる

## 0. **これも実装依頼ではない。測定依頼である。**

T1〜T3 の報告で数字が揃い、**案を1つに絞り込む材料がもう少しで揃う**ところまで来た。
本回で足りない1つ（案4）を測り、**4案を同じ表に並べる**のが目的である。

**U1 / U2 を終えた時点で止めて報告すること。** 実装は、4案が並んでから大杉さんが決める。

## 1. 前回の数字の読み直し — **Claude君の判断を1つ撤回する**

T2 の報告を受けて、私は「案3 は落としてください」と申し上げた。`cap_hard_sealed` の
3,000 だけを見て「繰り越しが自分を叩いた数」と判断した。**P合計を見たら、逆だった。**

```
              P合計     I_sum合計   CO合計   sealed   soft
baseline     100,501    100,501       0        0       0
案1/案2       98,501     35,501       0    2,000       0     <- 2,000 lot が消えている
案3          100,501     97,501       0    3,000       4     <- lot は残っている
```

**案1/案2 は 2,000 lot を削除する。案3 は削除しない**（P合計が baseline と同じ）。
案3 の 3,000 は「1つの lot が2週続けて封印判定に当たって二重に数えられた」結果で、
**lot 自体は生き残って翌週以降に流れている。**

**私は軸を1本しか見ていなかった。** 撤回して、軸を2本立てる。

```
                  lot を保存するか   sealed が「封じた量」を表すか   新たな歪みが出ないか
案1/案2                 ✗                      ○                          ○
案3                     ○                      ✗（真は2,000／表示3,000）    ✗（cap_soft 新規4件）
案4（未測定）           ？                     ？                         ？
```

**案1/案2 と案3 は、1本ずつしか満たしていない。だから、どちらも選びたくない。**

### I_sum の -65,000 が意味すること

案1/案2 で I_sum が 100,501 → 35,501 に落ちる。**2,000 lot を消すと在庫が 65,000
減る**（1 lot あたり約32週ぶん）。つまり**閉鎖週に作られた 2,000 lot は、その後ずっと
在庫に居座っていた**。案1/案2 はその死蔵在庫ごと消し、案3 は温存する（-3,000 のみ）。

### いちばん重い数字

**PPC 実現利益が4通りとも 1円も動かない（¥172,459,615.81）。**
これは U2 で扱う。

## U1. 案4 を測る — **P ではなく S（処理量）を絞る**

### 考え方

T1 で「型 A（9件）の `cap_hard` は自ノード自身の**加工スループット**（縫製・組立・
瓶詰）」と結論が出ている。**スループットの制約なら、絞るべきは入庫（P）ではなく
処理量（S）である。**

そして push ノードには**すでに在庫の仕組みがある**（`forward_planner.py` 505-506）。

```python
available = prev_inv_lots + p_lots
...
actual_s  = available[:total_cnt]
node.psi4supply[w][I] = available[total_cnt:]   # 余剰 -> 在庫
```

**余剰は I に落ち、翌週 `prev_inv_lots` として自然に戻る。** だから繰り越しの連鎖が
起きない——案3 が `CO[w+1]` 経由で起こした二重計上も、翌週の再判定も発生しない。

**「専用のペンディング在庫の設計が要る」という T2 の結論は、見直す価値がある。
既存の I がそれではないか。**

### 測るときの形（案）

Step 0a（P の切り詰め）は **push ノードでは触らない**まま、push 分岐の中で処理量を
絞る。

```python
cap_cnt  = int(ch) if ch > 0 else len(available)
actual_s = available[:min(total_cnt, cap_cnt)]
node.psi4supply[w][I] = available[len(actual_s):]
```

- `cap_hard` が処理量を実際に縛った週だけ `record_cap_hard_sealed()` する
  （**縛った量＝通せなかった量**。二重計上が起きない形にすること）
- 既存の `record_shortfall()`（需要に届かなかった分）との**役割の違いを明記**すること
  ——「能力で通せなかった」と「そもそも物が無かった」は別の事象である
- 型 A / 型 B の切り分けは、いまは**案2 と同じ軸**（T1 の型）でよい。
  属性をどこに持たせるかは実装時の議論なので、測定では判定をハードコードしてよい

**これは「こう実装せよ」ではなく「この形で測ってほしい」である。** 測った結果、
別の形のほうが素直だと分かったら、そう報告すること。

### 出してほしい表

**T2 と同じ列で、4案を1つの表に並べること。** これが本回の成果物である。

```

baseline      ...      ...        ...        ...              ...             ...
案1/案2       ...      ...        ...        ...              ...             ...
案3           ...      ...        ...        ...              ...             ...
案4           ...      ...        ...        ...              ...             ...
```

あわせて:

- **`Bottling_Noda` の I が閉鎖週の前後でどう動くか**（週次で W16〜W22 程度）。
  **2,000 lot が在庫に残って翌週以降に流れているか**が、案4 の成否そのものである
- golden 13ケースで動くのは soysauce 3件だけか（案1〜3 と同じか）
- **`cap_hard_sealed` が 2,000 になるか**（案3 の 3,000 のような二重計上が起きないか）

## U2. 在庫が損益に効いていない件を確かめる（**事実確認だけ**）

**2,000 lot の生産が消え、在庫が 65,000（65%）減っても、PPC 実現利益が1円も動かない。**

Claude君の側で先に確認した結果を書いておく。

- `wom/ppc/` に在庫保有コスト／保管費に相当する処理が見当たらない
  （`holding` / `carrying` / `inventory_cost` の実装はヒットしない）
- `ppc_kpi_summary.json` の項目は
  `total_revenue_base` / `total_cost_base` / `gross_profit_base` / `total_tariff_base` /
  `mom_profit_base` ほかで、**在庫に関する項目が1つも無い**

**確かめてほしいのはこの2点だけである。**

1. **PPC の原価に、在庫を持っていることによる費用が入る経路はあるか**
   （`cost_type` の一覧を出し、在庫に相当するものが有るか無いかを答えるだけでよい）
2. **無いとして、それは設計上の意図的な省略か、未実装か。**
   正典（`requests/` 配下・PPC の設計書）に記述があるか探して報告すること。
   **見つからないなら「見つからない」と書くこと**——それ自体が答えになる

**是非は判断しないこと。直さないこと。** これは S4 Evaluate（実現利益と差の分解）の
設計に直結するので、**S4 を作る前に事実を確定させておきたい**、という目的である。

「在庫を 65% 減らしても利益が1円も増えない経営コックピット」は、経営者に見せる画面
として成立しない。だが**それが欠陥なのか、意図した割り切りなのかは、まだ分からない。**
