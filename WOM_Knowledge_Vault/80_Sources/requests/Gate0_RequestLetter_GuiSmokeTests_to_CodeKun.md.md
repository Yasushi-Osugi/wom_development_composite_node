# Gate 0 Request Letter — GUI の Anti-Degrade 網

宛先: Code君
差出: Claude君
前提: Phase 8-2a 完了（fb6b2cb、442件全PASS）
種別: テストの新設のみ（`wom/` `tools/` は1行も触らない）

---

## 0. これは Code君の提案である

「Planning Engine の禁足コアを守る二重化（禁足ルール soft ＋ 3層テスト hard）と
同じ発想を GUI に適用すべきタイミング」という提案をそのまま採る。

私が出せなかった案である。私は「レビューを外すと自分の失敗を止める人が
いなくなる」というリスクに対して「測ってから書く規律」と「Code君の独立
レビュー」を挙げたが、**どちらも自己申告**だった。機械的な網はそうではない。

---

## 1. ただし「9件は機械検出可能だった」は半分だけ正しい

Code君は D1/D2/D3・C3/C4/C6 を「機械的に検出可能だった」としたが、
**欠陥を知った後に検証できること**と、**知らずに書いたテストが鳴ること**は
別である。

| | 知らずに書いた汎用テストで鳴るか |
|---|---|
| D3（操作行が窓外） | **鳴る**。「全ウィジェットが既定サイズに収まる」は盲目で書ける |
| C3（結論行365文字） | **鳴る**。「N文字を超えない」も盲目で書ける |
| C4（葉が空白の箱） | **鳴る**。「情報欄が空文字列でない」も盲目で書ける |
| D1（降りられない） | 鳴らない。「クリックできるべき」と先に思いつく必要がある |
| D2（wraplength 固定） | 鳴らない。同上 |

**この区別が本書の要件を決める。**

入れるのは**汎用の不変条件だけ**である。既知の欠陥をなぞるテスト
（「USD ノードの子に Button-1 があること」など特定の経路を名指しするもの）は
**入れない**——それは「もう直した場所」を守るだけで、S3/S4/S5 では鳴らない。
汎用の不変条件は次の画面でも鳴る。**次に鳴るかどうかが、この網の価値である。**

C3 について補足する。あの欠陥の本質は「行が長い」ではなく「**溢れた部分が
答えだった**」ことだった。文字数テストは症状しか見ないが、症状で止まれば
修正は始まる。それで十分である。一方「畳むときに配分ゼロ 6市場を残す」という
判断は機械では出せない——**この網は意味を判定しない。** そこは Gate 2（実機）の
役目のまま残す。Code君がそう明記していたのは正確である。

---

## 2. 作るもの

`tests/test_gui_panel_invariants.py`（名前は Code君の判断でよい）を新設する。

`AllocationPanel` を headless で実体化し、代表的な状態を通しながら
**構造として壊れていないか**だけを検査する。

### 通す状態（最低限）

| 状態 | モデル | node_path |
|---|---|---|
| triangle（N=3） | soysauce-jpy-2027-alloc | () |
| hierarchy 根 | oil-global-2027（uom=KL） | () |
| hierarchy 中間 | 同上 | ("EUR",) |
| **配分ゼロの枝** | 同上 | ("USD",) |
| **葉（出荷あり）** | 同上 | ("JPY","SP_Oil_Local","Retail_Local_KANTO") |
| **葉（出荷ゼロ）** | 同上 | ("USD","SP_Oil_US_Local","Retail_US_TX") |

### 検査する不変条件（すべて汎用・特定の画面を名指ししない）

1. **既定サイズに収まる。** `geometry("1280x820")` 相当で、全ウィジェットの
   `y + height` が窓の内側にある（D3 class）
2. **結論行が長すぎない。** `headline.lines_ja` の各行が上限文字数以内
   （上限値は Code君が実測して決めてよい。現行 98 文字に対して余裕を持たせる）。
   **全市場の控え欄も同じ検査にかける**——C3 の受け皿がここだからである
3. **情報欄が空でない。** どの状態でも、根拠パネル（図または代替メッセージ）と
   補助パネル（`_node_info_label` 相当）が空文字列にならない（C4 class）
4. **降りられる枝にはバインドがある。** hierarchy モードで子ノード行を出すなら、
   その行は必ず `<Button-1>` を持つ（D1 class）。**「子を出すなら」が条件**で、
   「USD の子を出せ」ではない
5. **リサイズに追従する。** `<Configure>` を発火させたとき、幅に追従すべき
   ラベルの `wraplength` が変わる（D2 class）
6. **例外なく描ける。** 上の全状態で `AllocationPanel` の描画が例外を出さない

### やらないこと

- **意味の判定をしない。** 「この数字が経営者にどう読めるか」は対象外
- 画像比較・スナップショット比較をしない（脆い）
- 既知の欠陥の再発テストを個別に足さない（それは各 Phase のテストの仕事）

---

## 3. 制約

- **`wom/` と `tools/` は1行も触らない。** テストだけを足す。
  検査のためにプロダクション側へフックを足したくなったら、**足さずに報告**
  してほしい——「テストのために本体を変える」を1回許すと、次から歯止めが無くなる
- **表示環境が無い場合は skip する。** CI や headless Linux で `tk.Tk()` が
  作れないときに失敗させない（`pytest.importorskip` / try-except + `pytest.skip`）。
  ただし**大杉さんの Windows では必ず走る**こと
- 遅くしない。既存442件の実行時間を大きく増やさない（目安: この網だけで
  数秒以内）。重くなるなら通す状態を減らしてよい

---

## 4. 完了条件

- 上の6条件が、6つの状態すべてに対して検査されている
- テストが特定の市場名・特定の node_path を「あるべきもの」として
  名指ししていない（データが変わっても意味を保つ）
- 表示環境が無い環境で skip され、ある環境で走る
- 既存442件は不変。`wom/` `tools/` の差分 0 行

## 5. 報告してほしいこと

1. 6条件のうち、**いま実際に鳴るものがあったか**（あれば、それが本 Phase の
   最初の収穫である）
2. 結論行の文字数上限をいくつにしたか、その根拠
3. 本体にフックを足したくなった箇所があったか
4. この網だけの実行時間
5. 最終テスト件数

回帰値は本書に書いていない。Code君が測った値を正典とする。
