## A. 酪農モデルにおける MOM 定義の見直し

### A.1 発案

india-ghee のサプライチェーンでは、WOM のモデル定義の考え方を見直す必要があるのではないか。
インド酪農の牛乳生産者は `leaf_in` ノードではなく、**それぞれが `MOM` ノード**として定義するのが本来的ではないか。

```
地域Xの牛の飼育
  → 地域Xの搾乳と牛乳出荷（MOM）
    → ghee 流通加工（Product Conversion）
      → [国内市場 / 海外市場]での在庫保管
        → 販売チャネルでの実販売
```

### A.2 構造の観察：酪農には BOM が無い

製造業の InBound は「部材 A + B + C を組み立てて完成品1台」という **BOM 型**。
酪農は「地域 A + B + C の生乳が単に足し算される」という **合流型**。

```
BOM 型    A(1) + B(1) + C(1) → 完成品 1     ← 揃わないと作れない
合流型    A(10) + B(20) + C(30) → 生乳 60   ← 揃う必要がない
```

**現在の `_propagate_to_parent` は、複数の子が親の `psi4supply[w][P]` へ独立に `extend()` する。
これは合流としては正しく、組立としては誤り。**

### A.3 したがって A1 の位置づけが変わる可能性がある

CLAUDE.md 記載の A1 原因仮説は「複数 leaf_in が独立に extend するため P が重複加算されて過大になる」だった。
しかし**合流型なら加算が正しい**。とすると A1 の本当の原因は、加算そのものではなく
**合流した後の CapHard シーリングの扱い**にある可能性がある。

Code 君の S2 調査で判明した機構（`_apply_mom_cap_backward` がオーバーフローの無い週には何もしない、
`_in_propagate` の `mom_constrained` ガードが P=S セルフコピーを一律スキップ）とも整合する方向。

### A.4 懸念：`node_type=mom` にすると別の挙動が発動する

`mom_constrained=True`（実運用の既定）のとき、`node_type=="mom"` のノードは
`_in_propagate` の P=S セルフコピーが**無条件でスキップ**される（S2 調査で確認）。

地域ノードを全て `mom` にすると、この挙動が全てに適用される。
**意味論として正しくても、実装上の副作用が読めない。**

### A.5 判断

**A1 の原因を確定させてから着手すべき。**
モデル定義を変えても A1 が消えない可能性がある。順序を誤ると、何が効いたか分からなくなる。

## B. InBound の組立工程（Assy Process）

### B.1 発案

部材の組立を考えた場合、**該当週の `P` にすべての部材からの Lot_ID が揃った状態で
Assemble する。つまり Lot_ID を一つにして、`I` 在庫として残す。**

### B.2 A との関係：逆の構造

| | A（合流） | B（組立） |
|---|---|---|
| 意味 | 同じものが複数経路から集まる | 異なるものが揃って一つになる |
| 揃わなかったら | 少ないだけ | **作れない** |
| Lot_ID | そのまま維持 | **一つに統合** |
| 典型 | 酪農の集乳、複数調達源 | 自動車・電機の組立 |

**現在の WOM には B の機構が無い。** ev-europe-2026（Battery / Motor / ECU の3 tier-1 が
1つの MOM に供給）が本来の対象だが、実質的に合流として処理されている。

### B.3 実装上の論点

**① 揃わなかった部材はどうなるか**

3部材のうち2つしか届かなければ組み立てられない。届いた2つは `I` に滞留する。
**これが部材待ち在庫であり、まさに可視化したいもの。**
（大杉さんの「ボトルネック吸収用の MOM 足元の部材在庫」という設計意図と一致）

**② 組立後の Lot_ID をどう決めるか**

Demand Anchored 設計では、需要側から来た Lot_ID が上流へ逆伝播している。
したがって**組立後は元の需要 Lot_ID に戻る**のが自然ではないか。
部材側は BOM 展開で別 ID を持ち、組立時に需要 ID へ合流する。

ただしこれは lot_id のスキーマ（`{sku_id}:{region}:{week}:{seq}`）と
identity matching の設計に触れる。**慎重な検討が要る。**

**③ 部材構成比（BOM 数量）をどこに置くか**

現在のスキーマには BOM 数量を表す列が無い。
`lane_assignment.csv` は leaf_out → MOM の振り分けであって、部材構成ではない。
新しいマスタ（`bom_master.csv` 等）が要る可能性。

### B.4 判断

**大きな機能追加。** 禁足コア（`forward_planner.py`）の変更を伴い、スキーマ拡張も必要。
A1 の原因確定と、A の判断を待ってから、正式な Request Letter として起票すべき。

## C. sweep loop の拡張：auto-debug から auto-tuning へ

### C.1 発案

今回作っている sweep loop の考え方を拡張して、**WOM の plugin pipeline の top routine にセット**すると、
**auto-debug 環境**に発展するのではないか。

さらに機能拡張すると、WOM の Planning → Simulation → Evaluation の後に、
CSV による planning parameters / constraints の定義を変更することで、
**planning space の auto-tuning 機能**として実装できるのではないか。

### C.2 三段階に分けて考える

```
①  sweep loop      変化点を振って結果を並べる           ← 2026-08-27 に実現
                   tools/sweep_flags.py

②  auto-debug      結果を判定基準に照らして異常を検出   ← 判定基準の定義が必要

③  auto-tuning     パラメータを探索して設定を決める     ← 目的関数の定義が必要
```

### C.3 ①→② の壁：「何が異常か」の定義

今日のスイープで CO_sum=1,260,626 を異常と判断したのは人間であって、ツールではない。
**ただし判定基準は書ける。** 今日見つかった症状が、そのまま判定ルールになる。

判定ルール候補（いずれも今日の観測から導出）：

```
[CO]   InBound の MOM ノードで CO が単調増加し、最終週まで解消しない
       → 擬似 CO の疑い。【異常】

[質量] 上流の生産量（leaf_in の P_sum）と下流の入荷量（DAD の P_sum）の差が
       閾値を超える
       → 例：C ケースで上流 +2,300 / DAD −1,150 の不整合を検出

[在庫] is_decoupling=True のノードで I が全週ゼロ
       → decoupling として機能していない。【警告】

[設定] is_decoupling=True かつ plan_mode="pull"（InBound）
       → 二点セット未成立。CO が単調増加する。【エラー相当】

[期間] warmup_lt < 最長チェーンの累積LT
       → 起動ランプ由来の CO。【警告】
```

**これらは静的 lint（CSV のみ）では検出できず、実行結果を見て初めて判定できる。**
すなわち auto-debug は、`docs/design/lot_id_traceability_and_coverage_views.md` の
三層可視化とは別の層に位置する。

```
静的 lint（第1層）    CSV を読むだけ         実行前
auto-debug            実行結果を判定         実行後   ← ここが新しい
E2E マトリクス（第2層） 網羅性を人間が確認     実行後
スイムレーン（第3層）   1ロットを追跡         実行後
```

### C.4 ②→③ の壁：思想

auto-tuning は「最適なパラメータを機械が見つける」ことだが、
これは WOM が意図的に捨てた道 —— **「最適化しない。地形を渡す」** —— に触れる。

**ただし、パラメータを二種類に分ければ矛盾しない。**

| 種別 | 例 | 扱い |
|---|---|---|
| **モデルが動くための設定** | `warmup_lt`、planning horizon、`cpu_size`、`transit_lt_wks` の既定 | **正しい値が一意に決まる。auto-tuning してよい** |
| **経営が決めるべき選択** | 配分比率、decoupling point の位置、安全在庫水準、調達地 | **地形として渡すべき。auto-tuning すべきでない** |

`warmup_lt` が累積LTより小さいと CO が出る、という知見は前者そのもの。
**機械が計算して設定すればよく、人間が手で決める理由がない。**

一方 decoupling point を MOM に置くか Node-X に置くかは後者。
DBR のボトルネック位置は経営判断であり、機械が決めるべきではない。

**この線引きが、WOM の思想と auto-tuning を両立させる条件。**

### C.5 判断

**三つの中で最も近く、投資対効果が高い。**

- ① は既に実現済み（`tools/sweep_flags.py`）
- ② は判定ルールを足すだけ。禁足コア無変更
- ③ は C.4 の線引きを守れば思想と矛盾しない

そして ② は **「大杉さん以外が WOM を使う」**という課題に直接効く。
人間が目視で異常を見つけるのではなく、ツールが指摘する。

## D. 三つの関係

```
        A1（multi-leaf_in × 需要段差の擬似 CO）
         │
         ├─ 原因確定が前提 ──→ A（酪農の MOM 定義）
         │                        └─ 意味論の整理 ──→ B（組立工程）
         │
         └─ 検出手段として ──→ C②（auto-debug）
                                  └─ 線引きを守れば ──→ C③（auto-tuning）
```

**A1 の原因確定が、A と B のボトルネック。**
**C は A1 と独立に進められる。** むしろ C② があれば A1 の再現・検証が機械化できる。
