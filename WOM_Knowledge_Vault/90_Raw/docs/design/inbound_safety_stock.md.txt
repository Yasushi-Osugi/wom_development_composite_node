# InBound Safety Stock：設定ルールと粒度制約

**実測にもとづく設計記録（2026-09-01）。コード変更なし。**

InBound Tree（`leaf_in → MOM → supply_point`）における安全在庫の設定方法と、
週次バケットに由来する粒度の制約を確定する。

**検証手段**：`tools/sweep_specs/bom_test_ss_days.json`、
`tools/sweep_specs/bom_test_ss_days_child.json`（`data/sample/bom-test-2026`）

---

## 0. 確定したルール

```
① InBound の安全在庫は、ss_days を「供給元の leaf_in」に設定する
   MOM 自身（InBound root）に設定しても完全な no-op

② 在庫は供給先（MOM）の I バケットに現れる
   設定した子ノード自身には立たない

③ ss_wks = ceil(ss_days / 7)
   1週未満の滞留は表現できない。3日も7日も1週分になる
```

---

## 1. 検証の経緯

### 1.1 動機

InBound 側で I（在庫）が正しく立つことを、**一度も確認できていなかった。**

- 2026-08-27：`buffering_stock_flag=1` 単独では CO が発生して失敗
- 二点セット（`push_lead_time_weeks` 併用）で立った I は、
  2026-08-30 の Mode4 修正（`44e67bf`）で**二重計上による幻**と判明

加えて、実務上の観察として次の指摘があった。

> 現実の世界では、仕掛在庫の滞留の様子、実際には一週間分ではなく、
> 2〜3日分の仕掛在庫が滞留している様子が、PSI の在庫 I として見えている、
> という状態が実際の現場の自然な姿だと思います。

**「機能が動かないのか、週次粒度の限界なのか」を切り分ける必要があった。**

### 1.2 検証1：MOM 自身に `ss_days` を設定 → **完全な no-op**

`data/sample/bom-test-2026` の `Vehicle_Assy`（mom、InBound root）の `ss_days` を振った。

| ケース | ss_days | Vehicle_Assy I_max | I_sum |
|---|---|---|---|
| base | 0 | 0 | 0 |
| ss3 | 3 | **0** | **0** |
| ss7 | 7 | **0** | **0** |
| ss14 | 14 | **0** | **0** |

106項目中、差分は `elapsed_sec`（実行時間ノイズ）の**1件のみ**。
対象5ノードの `series_md5` は全ケースで完全一致。

**上流の生産週も前倒しにならず、CO も PPC 金額も無変化。何も起きない。**

### 1.3 原因（コード読解、変更なし）

`wom/engine/backward_planner.py` に二つの独立した機構があり、
**どちらも MOM 自身の `ss_days` を拾わない。**

**① `B + X1 + X2` オフセット式（334-350行）**

コメントに明示的に **`[OutBound Tree only]`** と記されている。
親を持たない InBound root には元々適用されない。

**② 親→子への配置オフセット（453 / 471行）**

```python
child_w = self._offset_week(w, child.lt_wks + child.ss_wks, child.node_name)
```

**子（`Tire_Supply` / `Battery_Supply`）自身の `ss_wks`** を使う設計であり、
**親（`Vehicle_Assy`）の `ss_wks` は一切参照されない。**

### 1.4 検証2：子ノード（leaf_in）に設定 → **機能する**

`Tire_Supply` と `Battery_Supply` の `ss_days` を振った。

| ノード | I_max（base / ss3 / ss7 / ss14） |
|---|---|
| Tire_Supply | 0 / 0 / 0 / 0（**無変化**） |
| Battery_Supply | 0 / 0 / 0 / 0（**無変化**） |
| **Vehicle_Assy** | **0 / 10 / 10 / 20** |

生産週の前倒し：

| ケース | `P_nonzero_weeks` 開始週 | base からのシフト |
|---|---|---|
| base | 2025-W49 | — |
| child_ss3 / child_ss7 | 2025-W48 | **1週前倒し** |
| child_ss14 | 2025-W47 | **2週前倒し** |

CO は全ケース・全ノードで 0。

## 2. なぜ在庫は「親」に立つのか

### 2.1 機構

```
① 子は「親が本当に必要とする週」より ss_wks 週分早く供給するよう計画される
   （backward_planner.py 453/471 の child_w 計算）

② 子自身の S（出荷）と P（生産）は同じ週に動くだけで、
   子側には「早く作って留め置く」バッファは生まれない
   ＝ 子は単に「早い週に S=P を完了させる」だけ

③ そのギャップ（子が早く納入した週 〜 親が実際に消費する元々の週）が、
   親の P（早着した入荷）と S（本来の消費タイミング）の差分として現れ、
   I(w) = I(w-1) + P(w) − S(w) により親の I バケットに蓄積される
```

### 2.2 実務との対応

**タイヤとバッテリーが、車両組立の何週間か前に工場へ納入され、
組立ラインの脇（＝ MOM の足元）で部材在庫として滞留する。**

在庫は「送り出す側の倉庫」ではなく「受け取って使うまで置いておく側の倉庫」に立つ。
**物理的に正しい。**

これは 2026-08-27 に整理された次の設計意図と一致する。

> 「ボトルネック吸収用の MOM の足元の部材在庫」と
> 「需要変動吸収用の DAD の完成品在庫」の両方にバッファが立つのが自然な姿

## 3. 粒度の制約：週次未満の滞留は表現できない

### 3.1 実測

`ss3`（3日）と `ss7`（7日）で、`Vehicle_Assy` の `series_md5` が**完全に一致**した
（`596fb6645fe3`）。I_max も両方 10。

**`ss_wks = ceil(ss_days / 7)` により、3日も7日も 1週分になる。**

`ss14`（14日）では I_max=20 と**ちょうど2倍**になり、線形に反映されることも確認した。

### 3.2 したがって

実務では工程間に2〜3日分の仕掛在庫が滞留するのが自然だが、
**WOM では 0.3〜0.4週にあたるこの滞留を表現できない。**

無理に `ss_days=3` を設定すると、**1週分（実態の2〜3倍）の在庫が計上される。**

### 3.3 どちらが有害か

| | 影響 |
|---|---|
| I=0 と表示する | 実在する仕掛在庫が見えない。在庫評価・CCC が過小になる |
| 1週分を計上する | **実態の2〜3倍**の在庫が計上される。在庫評価・CCC が過大になる |

**過大な在庫を表示する方が、ゼロと表示するより有害である。**
金額（在庫評価、CCC、棚卸資産回転日数）に直接波及するため。

### 3.4 Weekly Granularity Thesis の境界

これはモデルの欠陥ではなく、**粒度の必然的な帰結**である。

```
経営が決めること     どこに decoupling point を置くか
                     どれだけバッファを持つか（週単位）

現場が管理すること   工程間の2〜3日の滞留
```

WOM は前者の粒度に合わせている。工程間の日次滞留は、経営判断の対象ではない。

**したがって「WOM の I=0 は、在庫が物理的に存在しないことを意味しない。」**

- 週次バケット未満の滞留は表現されない
- InBound の I=0 は「供給元に `ss_days` が設定されていない」ことを示すのであって、
  「仕掛品がゼロ」を意味しない
- 在庫評価・CCC の数字も、この分だけ過小になる

**これはモデルの限界として明示すべきものであり、V&V の粒度制約に属する。**

## 4. 運用ルール

### 4.1 MOM の足元に部材在庫を持たせたい場合

```
① ss_days を、その MOM に供給する leaf_in（各子ノード）に設定する
② 在庫は MOM 自身の I バケットに現れる
③ 週数は ceil(ss_days / 7)。最小単位は1週
```

**MOM 自身の `ss_days` を設定しても効果はない。**

### 4.2 複数の子がある場合

`bom-test-2026` の検証では `Tire_Supply` と `Battery_Supply` の両方に
同じ値を設定した。子ごとに異なる値を設定した場合の挙動は**未検証**。

各子の `child_w` が独立に計算されるため、子ごとに異なる前倒し量になると考えられるが、
確認していない。

### 4.3 `buffering_stock_flag`（decoupling）との関係

本書で扱った `ss_days` による在庫と、`buffering_stock_flag=1`（decoupling point）は
**別の機構**である。

| 機構 | 設定場所 | 在庫が立つ場所 |
|---|---|---|
| `ss_days` | 供給元の leaf_in | 供給先の MOM |
| `buffering_stock_flag` | そのノード自身 | Forward Phase1 の Demand-S copy 経由 |

後者は 2026-08-27 の調査で、**`push_config.csv` の行と併用しない限り
CO が単調増加する**ことが判明している。
本書の `ss_days` 方式は、それとは独立に、単体で正しく機能する。

## 6. lint 候補

```
[在庫] node_type=mom かつ ss_days > 0 で、親を持たない（InBound root）
       → MOM 自身の ss_days は参照されない。無効値である。
         供給元の leaf_in に設定すること。【警告】
```

**現在の全モデルで、InBound root に `ss_days` が設定されているものが無いかを
確認する価値がある。** 設定されていれば、それは無効値である。
