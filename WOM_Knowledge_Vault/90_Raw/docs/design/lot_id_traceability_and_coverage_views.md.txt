# v1r3m0：Lot_ID トレーサビリティ可視化の三層設計（設計記録のみ・実装なし、2026-08-18）

branch `wom-v1r3m0`。**本節は設計判断の記録であり、コード変更を一切伴わない。** エンジン・GUI・CSV スキーマはすべて無変更。次に実装へ進む Claude 君が、同じ検討を再走しなくて済むように、確定した事実・意味論・設計判断・罠を固定する。

## 背景

WOM の外部評価者（元IBM Thought Leader）から、実エンゲージメント投入に向けた要求として**一点だけ**指摘があった：

> インバウンドとアウトバウンドのネットワーク全体の網羅性と、PSI の Lot_ID 連携の全体感がイメージできる画面が欲しい。

この二つは別々の機能要求ではなく、実務上ひとつの問いである：**「この供給ネットワークに、意思決定上の穴がないことを、どうやって確認するのか」**。

大手製造業の経営会議で計画モデルを使う際、最初に問われるのは精度ではなく「これは全部入っているのか」である。拠点が漏れなく載っているか、拠点間で在庫が Lot 単位で受け渡されているか。ここが目視で確認できないモデルは、計算が正しくても経営判断の場では信用されない。

したがって本機能の位置づけは「計算機能」ではなく **「モデルの妥当性を第三者が納得するための可視化」**であり、コンサルティング・エンゲージメントの第一週で使う画面である。

## 1. Lot_ID データモデル：確定事項（`wom/model/lot_generator.py` 実装確認済み）

### 形式と一意性

```
lot_id = "{sku_id}:{region}:{week}:{seq:05d}"
         例  "Soy_Sauce:US_W:2027-W14:00042"
```

- `LotIDGenerator._counters` は **`(sku_id, region, week)` 単位**で採番。したがって lot_id は**全ランを通じて大域的に一意**。
- `LotIDGenerator.parse()` が正典のパーサ。**新規に自前パースを書かず、必ずこれを使うこと**（`sku_id`/`region` はハイフンを含みうるがコロンは含まない、という前提が埋まっている）。
- ロット数 = `ceil(qty / cpu_size)`（`assign_demand_lots_from_df`）。

### Demand Anchored：錨は leaf_out（市場側）

`assign_demand_lots_from_df` は `demand_forecast.csv` の `(sku_id, region, week)` から採番し、**leaf_out ノードの `psi4demand[w][S]`** に置く。そこから BackwardPlanner が LT オフセット付きで上流へ逆伝播し、工程間で ID を引き継ぐ。

**つまり lot_id が名乗っているのは「出発点（調達源）」ではなく「着地点（市場）」である。**

### 検討中に発生した誤解の訂正（次の Claude 君へ：同じ誤りを繰り返さないこと）

本セッションの検討途中で、以下三点の誤った前提が立てられ、後にコード確認で訂正された。記録しておく。

| 誤った前提 | 実際 |
|---|---|
| lot_id に product が入っていないので、製品ツリーを跨いだ lot_id 衝突を防ぐ lint が要る | **`sku_id` が先頭に入っている。衝突は原理的に起こらない。**該当 lint 項目は不要 |
| `_build_lot_leaf_index` の `lot_id.split(":")[1]` は region ではなく年を拾っている潜在バグ | **`[1]` は正しく region。あの実装は正常。** |
| lot_id は InBound leaf（調達源）を名乗っている | **leaf_out（市場）を名乗っている。**Demand Anchored の当然の帰結 |

### 帰結：leaf_in は lot_id からは分からない

lot_id をパースしても調達源は出ない。leaf_in を知るには **InBound 側の leaf_in ノードの PSI バケットを走査し、そこにいるロットの prefix を読む**必要がある。走査一回で済むため実装負荷は小さいが、「lot_id をパースすれば E2E が出る」という誤解をしないこと。

### 派生指標：需要週が埋まっていることの効用

lot_id の `week` は**需要週**である。したがって任意のノード・任意の週で、

```
先行週数 = lot の需要週 − そのロットが現在いる週
```

が引き算一発で出る。これは追加データなしに以下を可能にする：

1. **在庫を「時間」で表示できる** — DAD の I バケットにいるロット群の先行週数の平均 = そのノード・その週の在庫カバー週数。`B + X1 + X2`（`lt_wks + ss_wks + init_stock_wks`）の設計値と実測値を突き合わせられる。KPI フレームワークの「棚卸資産回転日数」への接続点でもある。
2. **CO を分類できる** — CO にいるロットの需要週を見れば、`需要週 < 現在週` = **遅延**、`需要週 ≥ 現在週` = **未着**、`需要週 < 計画開始週` = **立ち上がりランプの残骸** に機械的に切り分けられる。CLAUDE.md で複数回持ち越されている「CO 凍結か真の欠品か切り分け未完了」（oil-global の `Tank_EU_Local` W10=1907→W40=5372 等）は、**lot_id を読むだけで判定できる**見込み。

画面上は CO を単色の赤ではなくこの三色に塗り分ける。「赤いが問題ない赤」と「本当にまずい赤」が区別できることは、クライアントへの信用に直結する。

### メモリ負荷の見積り（懸念に対する結論：許容範囲）

| 項目 | 見積り |
|---|---|
| lot_id 文字列 1個 | 約 80 バイト |
| 醤油ケース（1,000 lot/週 × 104週 ≈ 10万ロット） | 文字列実体で **約 8 MB** |
| 各ロットの複数ノード・複数バケット・二層（demand/supply）への出現 | **同一文字列オブジェクトへの参照（8バイト/箇所）**。20〜30箇所でも +200バイト程度 |
| 合計 | **数十 MB のオーダー** |

Local-First（ローカル PC / Tkinter）アーキテクチャで十分扱える。iPhone や oil-global の 8 SKU でも桁は変わらない。

本質は「重い仕組み」ではなく **「ロット数は `qty / cpu_size` で決まり、モデル定義者が `cpu_size` で制御できる量」**である。醤油=1ケース、Hormuz/RedSea 原油=100,000 bbl のように業種ごとに物理的意味のある粒度を選ぶ限り破綻しない。危険なのは単位が「本」「個」のまま `cpu_size=1` でモデルを組んだ場合で、これは lint の検出項目とする（想定ロット数の事前見積り警告）。

なお、この O(ロット数) のコストは**トレーサビリティの対価であり、すでに正しさの代金として支払い済み**である。個数ベースに戻せばメモリは減るが、それは v1r0m4 の Lot_ID identity-matching 導入で根絶した「CO 凍結」バグの温床そのものである。

## 2. スキーマ意味論の固定（schema governance・**改名はしない**）

### `demand_forecast.csv` の `region` は地理ではない

`lot_generator._build_leaf_index` は `(sku_id, region) → leaf_out PlanNode` の写像を構築する。すなわち **`region` は「地理」ではなく「leaf_out ノードを一意に指すキー」として機能している**。

実データが裏付けている：ev-thailand-2026 の `Sales_TH_BKK`（現地生産チャネル）と `Sales_TH_BKK_i`（輸入チャネル）は**同じバンコク**であり、地理では区別できない。すでに `region` の実体はチャネル識別子である。

### 確定した意味論（正典）

```
demand_forecast.csv の region      = leaf_out ノード識別子（チャネル）。地理ではない。
(sku_id, region)                   = leaf_out ノードと 1:1 でなければならない（制約）
edge_cost_master.csv の src/dst_region、route_master.csv の region
                                   = 実際の地理（輸送レーン・仕向国）。上記とは別物。
```

**同じ列名で意味が異なる**。これは `node_type` が二系統（`procurement/mother_plant/...` と `mom/dad/leaf_in/leaf_out/supply_point`）ある構図と同型であり、すでに一度 World Map でバグを生んでいるパターンである。

### 概念的な読み替え（実装は据え置き）

データモデルの意味としては、lot_id は以下と読むのが自然：

```
実装:   {sku_id}       : {region}         : {week} : {seq}
概念:   {product_model}: {Out_Leaf_node}  : {week} : {seq}
```

現状の `{sku_id}:{region}` は「何が、何処に」を具体性をもって明示する base parameter 定義であり、これはこれで正しい。**概念側の名前に合わせた改名は行わない。**

**改名しない理由**：`Cols.REGION` を参照する全箇所に波及し、そのうち一部は本当に地理として `region` を使っている。上記の通り意味が二系統あるため、機械的な一括改名は新たなバグを生む。**仕様書側で意味を確定させ、実装は据え置く**（schema governance：仕様を公開しつつ改訂権を保持する、という WOM の防御的資産の方針と整合）。

### `product_model`：経営粒度の分離（**提案のみ・未実装**）

`sku_id` は物理フローの単位としては正しいが、**事業経営者が判断する製品粒度としては細かすぎる**。経営判断の粒度は Low_End / Standard / High_End といった製品モデルレベルである。

これは lot_id の粒度変更ではなく、**マスタに1列足す**ことで解決する：

```
sku_master.csv:
    sku_id, product_model, ...
    Soy_Sauce_Premium,  High_End
    Soy_Sauce_Standard, Standard
```

- PSI は **SKU 粒度のまま**（生産ライン・LT・歩留まりが違う以上、ここを丸めたら計画にならない）
- 集計だけをマスタ経由で `product_model` に上げる
- エンジン無変更。CSV に1列。

既存の設計思想と同型：PPC の `hs_code`（`route_master` 経由）、`ppc_node_profit_zone` の node→country も「実体は細かく、集約はマスタ経由」という同じ形をとっている。

## 3. 三層構成

問いの粒度が、層ごとに狭くなっていく。

```
第1層  静的 lint          「モデルは定義として成立しているか」
                          対象＝CSV のみ（Planning 実行前）
                          粒度＝モデル全体
                             ↓ 緑になったら Planning を回す
第2層  E2E マトリクス      「端から端まで繋がっているか」
                          対象＝全ロットの集計（走査1回）
                          粒度＝調達源 × 市場チャネル
                             ↓ 空セル／異常セルをクリック
第3層  スイムレーン        「このロットは、いつ、どこを通ったか」
                          対象＝ロット1本（または少数）
                          粒度＝ノード × 週 × バケット
```

**三層はそれぞれ別の人の問いに答える**（これが構成の根拠）：

| 層 | 答える相手 | その人の問い |
|---|---|---|
| 静的 lint | モデルを組んだコンサルタント自身 | 「定義に抜けはないか」（クライアントには見せない） |
| E2E マトリクス | クライアントの実務担当者・経営層 | 「うちの構造が正しく入っているか」 |
| スイムレーン | 計画・現場担当者 | 「なぜこの拠点は毎週欠品するのか」 |

外部評価者が網羅性と Lot_ID 連携を一息で述べたのは、**エンゲージメントの会話の順序をそのまま口にしたから**と考えられる。最初に構造の妥当性を認めてもらい（第2層）、次にその上をロットが流れる様子を見せる（第3層）。

### 第1層：静的 lint

**lint** は 1978年にベル研で C 言語用に作られた検査ツールの名。「lint」は衣類につく糸くず・毛玉のことで、「コンパイルは通るが、たぶん間違っている書き方」を拾う道具、という含意。**最大の特徴はプログラムを実行しないこと**（＝静的）。

WOM に置き換えると、**Planning Engine を回さずに CSV を読むだけでモデル定義の不備を指摘する検査**。建築でいう確認申請の図面審査に相当する。

**なぜ必要か**：WOM の事故のほとんどは「エンジンは正常に動くが、モデルが間違っている」という形をとり、**エラーを出さずに静かに間違った結果を返す**。CLAUDE.md に記録済みの実例：

- `holiday_calendar.csv` が存在しないノード名（`Sales_US_iPhone16`）を参照 → 無言で無視
- `capacity_plan.csv` に cap_soft 列がなくローダが読まない → 機能が休眠、無言
- `sc_tree_builder.py` が `init_stock_days` を読む配線を欠く → 同じく休眠、無言
- リネーム後に `detect_scenario()` が不一致 → 別シナリオへフォールバック、無言
- `sc_tree_master.csv` の `node_name` と `node_master.csv` の `node_name` が別物 → World Map の線が消える
- `lot_generator._build_leaf_index` が `(sku_id, region)` 重複を静かに上書き、`unmatched_keys` は記録されるだけで警告にならない → **需要が無言で消える**

**検査項目（案）**：

```
[構造] node_master と sc_tree_master のノード集合差分（join key は node_id ≡ node_name）
       parent_node が空で root でもないノード（孤立）
       mom root ↔ supply_point root のブリッジ対応（product_name 一致）
[参照] holiday_calendar / capacity_plan / route_master / lane_assignment が
       実在しないノード名・SKU名を参照していないか
[需要] (sku_id, region) と leaf_out ノードの 1:1 検査（重複＝上書き、不一致＝unmatched）
[語彙] node_type の二系統（map 用語 / WOM 用語）の整合
[規模] cpu_size と demand から想定ロット数を試算、閾値超で警告
[欠損] lat/lon、leaf_out の region、必須CSVの不在
[BOM] supply_role=confluence かつ bom_qty > 1
      → confluence は需要を分担する型であり、倍率は意味を持たない。【エラー】
[BOM] bom_qty が正の整数でない（0、負数、小数）
      → 【エラー】
[能力] max_supply × cpu_size × bom_qty が cap_pieces と一致しない（誤差1単位超）
      → 換算誤りの疑い。【警告】
      cap_pieces が空欄の場合は検査しない
[単位] uom ラベルが実態と食い違っている
      → oil-global の Hormuz / RedSea が KL のまま（実体は10万バレル相当）
      → 機械判定は困難。目視確認項目として記録
```

上記のうち `[BOM]` 2件・`[能力]` 1件・`[単位]` 1件は Request Letter B
（`requests/request_letter_b_bom_qty.md` §7、"1 set rule" — per-node BOM
quantity N）で追加された項目。lint 自体は本節時点でも未実装のまま
（§6 item 4 参照）。

実行時間は数秒。**エンジンにも lot_id にも一切依存しない**（＝最も早く着手できる層）。

lint は**警告であって禁止ではない**（設計判断 D4 参照）。

### 第2層：leaf_in × leaf_out マトリクス

**目的は一つ：一枚の表で「この供給網に穴がないか」を判定できるようにすること。**

**なぜツリー図ではなく表か**：ツリー図はノードが増えると読めなくなる。線の数はノード数の二乗で増える（oil-global を World Map で開いた際に実際に発生した問題。SKU フィルタ導入の動機そのもの）。

一方、クライアントの実務担当者が確認したいことは実はツリーの形ではなく、**「うちの調達先が全部載っているか」「うちの市場が全部載っているか」「その組み合わせが正しいか」**の三つである。これは端と端の対応関係の問題であって、中間経路の問題ではない。だから中間を潰し、端と端だけの表にする。

```
                  Rest_US_W  Rest_US_E  Rest_JP  Rest_FR  Rest_NL
Materials_JP         1,820      1,820     3,120      780      520
Crude_ME_Hormuz          -          -         -        -        -   ← 空行
Soy_Import_CN            -          -       120        -        -
```

**読み方**：

- **空行** = その調達源から何も出ていない → 定義したが未使用、または結線ミス
- **空列** = その市場に何も届いていない → 需要があるのに供給経路が繋がっていない
- **想定外に埋まっているセル** = 意図しない経路が通っている
- **想定通りのセル** = 確認完了

**サイズは行数×列数で安定する**（oil-global 8 SKU でも 10行×20列 ≒ 200セル程度）。ノード数がいくら増えても、端の数しか増えない。人間が5分で目を通せる。

**期間で切ると代替ルート転換が見える**：Hormuz/RedSea ケースでは W14 までは `Crude_ME_Hormuz` 行が埋まり、W19 以降 `Crude_ME_RedSea` 行に移る。ルート転換が一枚の表の重心移動として現れる。

**軸の二段階化**（`product_model` 導入後）：同じ索引から二枚が出る。

```
経営レイヤー: product_model × 市場グループ   → 数十セル、経営会議用
実務レイヤー: sku_id        × leaf_out       → 数百セル、実務担当者の確認用
```

**この二枚をドリルダウンで繋げられることが、本画面の商品価値**。経営層に粗い一枚で合意を取り、実務担当者には細かい一枚で妥当性を確認してもらう。同じデータの二つの読み方であることが保証されるので、会議で数字がずれない。

**列は lot_id のパースだけで確定する**（region が入っているため）。行（leaf_in）だけを InBound 側 PSI バケットの走査で解決する。

### 第3層：スイムレーン・トレース

横軸＝週、縦軸＝レーン順（`leaf_in → MOM → supply_point → DAD → leaf_out`）のグリッド。

**ロット単体モード**：選択した lot_id が出現するセルを bucket（P/S/I/CO）別に色分け。上流ほど早い週、下流ほど遅い週に印がつくため、**階段状の斜線**が描かれる。**この斜線の傾きがそのままリードタイム構造**であり、`B + X1 + X2` のオフセット設計が目に見える形になる。CO に滞留したロットは**横方向の赤い連続**として現れる（「このロットは DC で6週間詰まっていた」が一目で分かる）。各セルに先行週数を持たせれば、設計上の LT と実際の先行週数のズレも同じ画面に出る。

**集計モード**：同じグリッドにロット件数の濃淡を敷く。行全体が真っ白なノード＝定義されているのに一度もロットが通っていない（＝第2層の空行を、時間軸つきで見た姿）。

既存の `NetworkPanel`（NetworkX Hammock グラフ）は**構造**を見る道具として残し、本パネルは**構造の上を時間軸でロットが流れる様子**を見る道具として別に立てる。目的が異なるため同じ画面に無理に載せない。

## 4. 確定した設計判断

### D1：lot_id の形式は変更しない

`product` を lot_id に足す案を検討したが、**不要かつ有害**と結論。

1. **不要** — WOM のエンジンは全処理が製品スコープ（`run(prod_nm)` / `get_ot_root(prod_nm)`）で動き、同一物理拠点でも製品が違えば別ノードとして複製する運用が徹底されている（`Refinery_Local_H` / `_R`、`Sales_TH_BKK` / `_i`）。**あるノードは必ずただ一つの製品ツリーに属する**ため、`product` はノードから常に復元できる。復元可能な情報を ID に埋め込むのは冗長化。そもそも `sku_id` が既に入っている。
2. **検索性が落ちる** — 現形式は先頭が `sku_id` なので**前方一致で絞り込め、ソート順も自然**（SKU → 市場 → 時系列）。要素を前置すればこの性質が壊れる。
3. **メモリが増える** — lot_id は PSI バケットの `List[str]` の中身そのもので、全ノード×全週ぶん存在する。文字列長の増加は identity matching の集合演算のハッシュコストにも効く。
4. **golden が全滅しうる** — `tests/golden/*.json` の `series_md5` が lot_id 文字列を含んでハッシュしているなら、挙動が何も変わっていないのに12ケース全てが赤くなる（**要確認事項**、後述）。

前例とも整合：`PPCEvent` は `product_id` を ID に混ぜず独立フィールドとして持っている。

### D2：逆引き索引は製品スコープで入れ子にする

```
index[product][lot_id] → [(node_id, week, bucket, layer), ...]
```

- 外側の dict は製品数ぶん（数個）のみ
- 内側のキーは**既存の lot_id 文字列オブジェクトへの参照**なので、新規の文字列アロケーションはゼロ
- タプルキー `(product, lot_id)` より軽く、製品単位で丸ごと破棄できる
- 既存の `_build_lot_leaf_index(ot_root)` が OT ツリー1本を引数に取る流儀と揃う

### D3：索引は常駐させない

- **第2層（網羅性・集計）に索引は不要** — ノード×週×バケットの件数は `len()` で出る。マトリクスは lot_id の prefix を数える走査1回で作れ、結果は数百セルの表。
- **第3層（トレース）は要求時に計算すれば十分** — 1本のロットの経路は、そのロットが属する製品ツリーだけを走査すれば出る（12ノード × 156週 × 4バケット程度なら GUI 応答として瞬間）。
- **スコープは既存の SKU ドロップダウンが与える** — Management タブと World Map で確立済みの UI 規約に索引の寿命を合わせる（SKU 選択で構築、切替で破棄）。ユーザーの見方と索引の生存期間が一致するので説明も不要。

**美しさの観点での結論：新しい状態を持たない。** PSI バケットが唯一の真実源であり続け、索引は一時的な読み方に過ぎない、という関係を保つ。

### D4：lint は警告であって禁止ではない

既存モデルを一つも壊さないこと、および「黙って解く黒箱にしない」という WOM の一貫した方針（`init_stock_days` の手動調整優先、自動調整は上書き可能な提案として併存）に従う。lint はブロックせず、指摘するに留める。

### D5：v1 は禁足コアに触らない

三層とも**加算のみ・読み取り専用**で、保護対象6ファイル（`backward_planner.py` / `forward_planner.py` / `plan_copy.py` / `plan_node.py` / `sc_tree.py` / `push_pull.py`）は無変更。特に第1層は CSV しか読まないためエンジンとの接点がゼロ。golden 12ケースは当然不変。

## 5. 実装上の制約と罠（実装する Claude 君へ）

- **`app.py` に足さないこと。** すでに約3900行・170KB超で、bash マウント越しの切り捨て問題の震源地。純ロジックを **`wom/analysis/`（tkinter 非依存）** に置き、`wom/gui/` 側には薄い Panel を**新規ファイル**で作る。
- **純ロジックを分離すると `tools/run_headless_from_folder.py` から呼べる。** これが効く：カバレッジ結果を **CSV エクスポート**できる＝エンゲージメント初週にクライアントへ提出できる成果物になる。画面は説得の道具だが、CSV は納品物になる。テストも書ける。
- **CO は supply 層のみを使うこと。** demand 層の CO は Backward の carry-back でカスケード計上され、純 displacement より大きく見える（CLAUDE.md 既出）。欠品として画面に出すのは `psi4supply[w][CO]` に限定する。ここを混ぜると「欠品が実際より多い」画面をクライアントに見せることになる。
- **ISO 週の復元は `date.fromisocalendar` を使うこと。** 2027 は W52 まで、2026 は W53 まで。OPEC+ パッチで週ラベルを文字列組み立てして84行中18行しか一致しなかった件と同型の罠があり、しかも索引側では**サイレントに「そのロットは存在しない」扱い**になるため発覚がさらに遅れる。
- **パースは `LotIDGenerator.parse()` を使うこと**（自前 split を書かない）。
- **warm-up 未設定の旧ケースは赤く光る。** oil-global 系などは起動ランプ由来の CO が大量に出る（`warmup_lt` で解決済みの既知現象）。**デモで開くケースは事前に warm-up を通しておくこと。**`soysauce-jpy-2027` は済んでいるのでデモ第一候補。
- **v1 のトレースは「計画上の経路」である。** DAD / leaf_out の `psi4supply[w][S]` は Lot_ID identity-matching 導入以降、意図的に需要アンカー型（計画値）のままで、実出荷は `ForwardPlanner._actual_s`（GUI 非露出の内部 dict）にしかない。下流末端の実出荷経路を出すには v2 で `_actual_s` を露出する必要がある（下記）。
