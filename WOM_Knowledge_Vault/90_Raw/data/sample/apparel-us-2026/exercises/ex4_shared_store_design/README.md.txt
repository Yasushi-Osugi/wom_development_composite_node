# 課題④ 店舗共有パターンの設計

## 課題文
本モデルでは両ブランドの店舗ノードを別々（`_I` / `_L` サフィックス）にしていますが、
「同一小売業者が2ブランドを展開し、同じ物流拠点・店舗網を共有する」という設定に
変更する場合、`lane_assignment.csv` の優先順位ロジックをどう再設計すべきか考えてみましょう。

これはコードで一意に検証できる問題ではなく、設計判断を問う討議課題です。以下は模範解答
の一例（唯一の正解ではありません）。

## 模範解答（設計討議）

### 現状の構造
現行モデルでは、Apparel_Outsourced（H&M型）と Apparel_Integrated（Zara型）は、
`SP_Apparel_Outsourced` / `SP_Apparel_Integrated` という別々のSupply Pointから、
別々のDC（`DC_Import_Buffer` / `DC_Local_US`）、別々の店舗ノード
（`Sales_US_TX_I` / `Sales_US_TX_L` 等）へと、完全に独立した経路で流れています。

### なぜ単純に「ノードを統合」できないか
2ブランドは、輸送モード・リードタイム・セーフティストックがまったく異なります
（Outsourced: 海上輸送・約15週・ss_days=21、Integrated: 航空輸送・約3週・ss_days=7、
第4回課題③参照）。DCを1つに統合すると、この異なる補充カデンス（入荷頻度・ロット
サイズ）を同じ物理施設内で扱うことになり、PSIロジック上は「1つのノードなのに
2つの補充パターンが混在する」という状態になります。したがって、**物理拠点は
共有しても、PSI上のノード（＝在庫管理の単位）はブランドごとに分けたまま**にするのが
安全です。

### 提案する再設計
1. **物流拠点（DC）の共有** — 物理的に同じ倉庫を使う場合でも、SC Tree上は
   `DC_Shared_US` のような1つの `node_name` に統合するのではなく、
   `node_master.csv` に「同じ `physical_facility_id` を共有する複数の論理ノード」
   という概念を追加する。PSI計算（在庫の入出庫）はブランドごとに独立したまま、
   `physical_facility_id` 単位で庫内作業キャパ（入荷ドック数・ピッキング能力）を
   合算してシーリングする。これは課題③で発見した「SKU単位で独立判定される」問題
   への対処と同じ発想です。

2. **店舗（Sales node）の共有** — 「同じ店舗で2ブランドを売る」場合は、棚割り・
   販売員のオペレーションキャパシティが共有制約になります。`lane_assignment.csv`
   に `shared_capacity_pool_id` 列を追加し、同じ物理店舗を指す複数ブランドの
   `Sales_*` ノードをグルーピング。店舗搬入トラックの積載量やバックヤード保管
   スペースなど、実際にボトルネックになる資源を明示的にモデル化する。

3. **優先順位ロジック** — 共有キャパシティを2ブランドが取り合う場面（例:
   トラック1台に両ブランドの荷物が乗り切らない）では、単純な早い者勝ちではなく、
   優先順位を明示的に定義する必要があります。候補となる優先ルール:
   - **粗利貢献優先**: 単位輸送コストあたりの粗利が高いSKU/ブランドを優先
   - **季節クリティカリティ優先**: 需要ウィンドウの残り期間が短い（売り逃すと
     販売機会を失う）SKUを優先
   - **固定比率分割**: ブランドごとに輸送キャパシティの取り分をあらかじめ契約的に
     決めておく（実務でも複数ブランドを展開する小売業者はこの方式が多い）
   `lane_assignment.csv` に `priority_rank` 列と `allocation_method`
   （`priority` / `fixed_ratio` のいずれか）を追加し、`LaneAssignment` クラス
   （`wom/engine/lane_assignment.py`）にこの列を読んで割当を決めるロジックを実装する、
   というのが具体的な拡張案です。

4. **段階的な導入順序** — いきなり店舗まで統合するのではなく、まず物流拠点（DC）
   の共有から着手し、実際に共有キャパシティの奪い合いが起きるシナリオ（繁忙期の
   同時ピーク等）で優先順位ロジックが意図通り動くかを検証してから、店舗レベルの
   共有に進むのが実務的にもリスクが低い進め方です。

### この課題が示すこと
本モデルの現在の設計（ブランドごとに完全独立したノード）は、「まず個々のブランドの
経済性を正確にモデル化する」という第6回記事の目的には最適でした。しかし複数ブランド
の**シナジー**（共有インフラによるコスト削減）を評価したい場合は、このままでは表現
できません。課題③で見た「SKU単位で独立にキャパシティ判定される」という設計上の
限界は、単なるバグではなく、「まだ共有キャパシティという概念自体がモデルに存在しない」
ことの表れです。これをどう拡張するかは、次回以降のテーマ候補です。
