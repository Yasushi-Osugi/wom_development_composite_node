## K1. 「現状維持」→「成り行き」

```
現行:  現状維持（需要どおり配る） 72.3億 に対し +52.7億（+72.9%）
改訂:  成り行き（需要どおり配る） 72.3億 に対し +52.7億（+72.9%）
```

**理由**: 実装は「需要比例」であって「いまのやり方」ではない。その会社が実際には
特定市場を優先しているなら、`P_bau` はその会社の BAU ではない。「現状維持」は
「いまのやり方を続ける」と読めてしまう。

**「成り行き」は日本の経営で「成り行き予算」「成り行き計画」として、まさに
「意思を入れず、そのまま延ばした場合」の意味で使われる語である**（大杉さん判断）。
`P_bau` が表すのは**配分に意思を入れないこと**であって、過去の踏襲ではない。

図の凡例（`現状維持（需要比例配分）`）も同様に直すこと。**語は1箇所に定義し、
結論行・凡例・docstring から参照する**形が望ましい（2箇所に書くと片方だけ直る）。

なお `P_bau` という**実装名は変えない**。設計書 §2.5 の `H_willbe` との対応も
そのまま（`H_willbe = P_bau`）。変わるのは画面に出る日本語だけである。

## K2. 子ノードでは「利益水準」を出さない（**V1.1 の一部改訂**）

### 大杉さんの指摘

> ドリルダウンして JPY/EU/US と入った時に、"利益水準は全体の値" というのは、
> オブジェクト指向の GUI の原則からハズレています。そのような内容なら、
> **そもそも表示しない方が、誤解を招かない、経営判断を誤らないためにも良い**

### これは私の設計（V1.1）より強い

Phase 8-1 で私はこう決めた（`build_s1_view()` の docstring）。

> **`headline` と `levels` は `node_path` を変えても変わらない**（V1.1）。
> ノードを降りるたびに結論行の金額が変わると、経営者が「いま見ている数字が
> 全体なのか一部なのか」を見失う。

**危険の認識は同じで、解が逆である。**

```
V1.1        全体の数字を「変えない」ことで解く
大杉さん案  全体の数字を子ノードに「出さない」ことで解く
```

**出さないほうが強い。** 変えないだけでは、読み手が「これはこのノードの値だ」と
誤読する余地が残る——実際、EUR ノードで `P_opt 125.011 億` が無印のまま出ている。
これは Phase 8-2 の C1（結論行と子パネルが別々の配分を無印で並べていた）と
**同じ家族**である。私は C1 を直しながら、隣で同じ形を残していた。

前便で私が提案した「根ノード以外では `P_bau` に（全体の値）と添える」は
**取り下げる**。註釈で救うより、出さないほうが正しい。

### 直すこと

**`node_path` が空でなければ、`levels` と `level_notes_ja` を出さない。**

```
build_s1_view()
  node_path == ()    levels / level_notes_ja  あり（ノード = 木の全体なので正しい）
  node_path != ()    levels / level_notes_ja  空
```

triangle モード（N=3）は `node_path` が常に `()` なので影響を受けない。

パネル側は、`levels` が空なら**「利益水準」の見出しごと隠す**こと
（見出しだけ残ると、中身が無いブロックになる）。

### 全体の文脈は失われない

③結論行は**常に上にある**。`利益 125.011 億`（P_opt）も、階層化の誤差の1行も、
判断反転の1行も、降りても消えない。**消えるのは⑤補助パネルの内訳だけ**である。

```
③結論行        全体の結論      常時（V1.1 のまま・改訂しない）
⑤補助パネル    このノードのこと  子ノードでは「このノードの走査結果」だけ
```

**`headline` の不変（V1.1 の本体）は維持する。** 改めるのは `levels` /
`level_notes_ja` の扱いだけである。

### 片肺が自動的に解ける

いま子ノードでは「図に ◆ が無いのにパネルに `P_bau 72.321 億` が出ている」という
ちぐはぐがある。K2 でパネル側も消えるので、**整合する**。

なお、子ノードに BAU を射影する案は**申し送りのままとする**。EUR ノードの
線分図は「EUR の能力 62,400 lot」を前提にした曲線で、BAU なら EUR に回る量は
違う。**BAU が持たない能力を前提にした曲線の上に BAU の点を打つ**ことになり、
これも C1 と同じ形の誤りになる。正しくやるなら BAU 自身の地形をもう1枚描く
必要があり、1枚に重ねられる話ではない。

### テストの更新

`tests/test_s1_view_model.py` の V1.1 テストが `levels` の不変を固定している。

```python
assert all(h == headlines[0] for h in headlines)   # headline は不変のまま（維持）
assert all(l == levels[0] for l in levels)          # <- ここを改める
```

改訂後は「**`levels` は根にのみ存在し、子ノードでは空**」を固定すること。
`headline` の不変は**そのまま残す**（V1.1 の本体なので）。

`build_s1_view()` の docstring の V1.1 の記述も改めること。**他にも V1.1 に
言及している箇所があれば全部直し、どこを直したか報告してほしい**
（1箇所だけ直すと、残った記述が嘘になる——Phase 8-3a のフォント設定で
実際にそれが起きた）。

## K3. 小さい額で桁が落ちる

```
oil       成り行き（需要どおり配る） 72.3億 に対し +52.7億（+72.9%）
soysauce  成り行き（需要どおり配る）  1.2億 に対し  +0.1億（+10.2%）
```

soysauce の `+0.1億` は実際には **12,589,119 円**である。`{x/1e8:.1f}億` 固定なので、
億単位のケースでは3桁出るのに、億に届かないケースでは1桁しか残らない。
**「+0.1億」は「ほぼゼロ」と読まれる。**

億に満たない額では単位を落とす（`+1,259万` など）か、有効数字を確保する形に
すること。方式は Code君の判断でよい。要件は「**どのケースでも、金額の大きさが
判断できる桁数が残る**」こと。

`_format_bau_gap_ja()` の中だけで閉じるはずである。
