## 4. 見込みとの比較

| 見込み | 結果 |
|---|---|
| P0 は C3a と同じ数 | **どおり**（§3.2） |
| P1 の ③＝タイ 104・88 | **どおり** |
| P1 の ② の合計は能力の合計と同じなので、⑤＝0 | **外れた：⑤＝4（各 SKU 2）** |
| 作り置き・年齢は C3a と同じ程度 | **どおり**（278・205、28 週） |

**⑤ が 0 にならなかった理由**（依頼書 §4 の「合計ではなく週ごと（累計）の条件」に当たる）：

1. **最後の 2 週の余裕が使えない**。P1 では工場の 2029-W47・W48 の需要が 12・9 で、上限より 1 lot ずつ少ない。この 2 週が作るのは市場の 2029-W51・W52 の分だが、直営店の lot は店頭在庫（`ss_days`＝14）のぶん 2 週早く作るので、W51・W52 の直営店の分は W45・W46 に回っている（W53 以降の需要は無い）。Backward の押し戻しは**前の週にしか動かない**ので、この 2 週の余裕を埋める需要は無い。**この需要の形での実際の能力は 2,184 ではなく 2,182（Cream 1,678）**。
2. **押し戻しが計画の最初の週に入る**。その 2 lot の超過は押し戻されて計画の最初の週 2026-W37 に置かれる。Backward はこの週にも能力（13・10）があるとして置くが、原料の区間（1 週）のため、Forward はこの週に作れない。そのまま出荷されず ⑤ になる。押し戻しの最後尾は一番遅い需要の lot なので、⑤ はタイの 2029-W50 の要求になった（試行 2・C3a と同じく、どの lot が残るかは押し戻しの順で決まる）。

**参考 P1r で確かめた**（P1 からタイを各 2 lot 追加で減らす）：

- Cream：⑤＝0 になった（③ 90、④ 1,678）。上の説明どおり。
- Serum：⑤＝2 のまま。減らした 2 lot が、週の形に比例して散らす規則（最大剰余法）で **2029-W51・W52 に当たり**（タイの週の需要 3 → 2）、それはちょうど余裕のある工場の 2 週が作る市場の週だった。余裕は 2 → 4 lot に増え、ほかの週の能力は空かなかった（工場の上限いっぱいの週は 166 のまま、P の合計 2,180）。

→ **⑤ を 0 にするには、合計を能力に合わせるだけでは足りない**。どの週の需要を減らすか（業務の判断）と、計画の始まり（原料のリードタイム）と終わり（店頭在庫の時間）の端の効果が、結果を決める。今の道具は週の形に比例して減らすだけで、どの週を減らせば ⑤ が 0 になるかは選ばない。

## 5. 止める理由と申し送り

**止める理由**：無し（道具は不整合なしで終了、P0 は V09 と同じ、① は 390・299、期間・能力の固定は保たれた）。

**申し送り**：

1. **`tools/shelf_life_check.py` に `--demand-file`（と `warmup_real_start`）が無い**。数量配分モードで作った需要 CSV の計画を CLI で測れない。今回は `check_tree()` を同じ設定で計画した木に当てた。数量配分モードと組み合わせるなら、CLI に需要 CSV を渡す引数を足す（コードの変更、別の依頼）。
2. **Backward は計画の最初の週に能力があるとして置くが、Forward はその週に作れない**（原料の区間 1 週）。押し戻しの最後尾がそこに入ると、Backward の段階では past due にならず、Forward で ⑤ になる。どちらの記録にも「計画の最初の週に置いたが作れない」とは出ない（今回は lot の追跡で見つけた）。InBound のリードタイムの分だけ計画の最初の週を能力ゼロとして扱うか、記録を足すかは保護対象コア（Backward）の話。
3. **配分を週へ散らす規則**（週の形に比例、最大剰余法）は、端数の行き先で ⑤ を変える（P1r の Serum）。どの週から減らすかを業務の規則として持つなら、配分のファイルに期間の列（週ごとの `alloc_lots`）が要る（依頼書 B の「期間の一部だけを配分する機能は作らない」の先の話）。
4. 未配分の扱い（D18）は、状態の JSON の `unallocated_treatment` に仮定として記録した。道具は扱いを決めていない。
