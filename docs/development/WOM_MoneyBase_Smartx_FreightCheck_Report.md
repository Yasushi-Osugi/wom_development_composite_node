## 2. Q2：同じ輸送か

**決められない。** 分かったことと、分からないことを分けて書く。

分かったこと（経緯）：

1. **最初の版（`a28062c`、2026-07-02）から、二つの運賃は 3 製品すべてにあった。** ノード `DC_AMER` 100,000（備考 Ocean freight CN→AMER + port handling）、区間 `SP_SmartXPro->Retail_AMER` 170,000 など。SmartX・SmartXNext も同じ形（例：`DC_AMER_g1` 95,000 と `SP_SmartX->Retail_AMER_g1` 161,000）。区間／ノードの比は 9 組すべて 1.65〜1.80 で、同じ作り方で一度に作られたデータに見える。
2. **その時点では、区間の行は一度も引かれていなかった。** 区間の鍵が supply point 経由（`SP_…->Retail_…`）で、PPC が作る鍵（工場 → 最初の DC、DC → 市場）と合わなかった（`requests/smartx-2027-2029-fix-request-letter.md` 263 行「ルックアップが常に空振り」）。計上されていた運賃はノードの分だけ。
3. **`55ae30c`（2026-07-11）で SmartXPro だけ、区間の鍵を実在の区間に付け替えた**（`tools/split_smartx_sku.py` 227〜304 行。旧 `SP_SmartXPro->Retail_AMER` 170,000 → `AssemblyIN->DC_AMER`「国際輸送費」）。ここで区間の運賃が初めて計上され、ノードの運賃と並んだ。**このとき、ノードの運賃との関係は検討されていない**（依頼書・スクリプトに記述なし）。ノードの備考は SKU の付け替えでそのまま引き継がれた（AMER の「CN→AMER」がインド組立の製品に残ったのはこのため）。
4. 同じ日に全製品の金額を 1/10,000 にした（`tools/fix_smartx_price_scale.py`）。ノードも区間も同じ倍率。

読み方は二つあり、資料では選べない：

- **同じ輸送（重複）**：ノードの備考は「Ocean freight CN→…」で、移行の記録は区間を「国際輸送費」と呼ぶ。どちらも工場から DC までの国際輸送。
- **別の費用**：元のデータは区間を supply point → 市場（DC を通り越した全行程）に、ノードを DC に置いていた。作った人が「全行程の運賃」と「DC 側の港湾取扱・通関など」を分けたつもりだった可能性は消せない。ただし備考の主語は 3 行とも「freight」で、取扱・通関は AMER・EMEA の添え書きだけ、APAC は運賃だけ。

積算の根拠（内訳・請求）はリポジトリに無い。README にも運賃の説明は無い。なお、Management の Landed Cost 用の `edge_cost_master.csv` には別の運賃（CN→AMER 50、EMEA 40、APAC 25 USD／lot）があり、三つ目の数字。PPC とは別の台帳で、今回の額には入らない。

**大杉さんへの問い**：このモデルで、工場から DC までの国際輸送の運賃は 1 台当たりいくらのつもりか（AMER なら 17・10・27 のどれか）。DC の 10・8・12 を「港湾取扱・通関など DC 側の費用」として残す意図はあるか。

- ノードに運賃があるモデル：bom-test 2 行、ev の 3 モデル各 4 行、oil 16 行（区間の行は 0）、smartphone-global 16 行（区間 12 行、対になる組は 0）、smartx 16 行（区間 14 行、対 3）。

## 4. Q4：影響の額と単位

全体（golden と同じ）：売上 700,825,463.00、費用 67,503,725.76、粗利 633,321,737.24、粗利率 90.368%。

| もし重複なら | 過大な費用（＝過小な粗利） | 費用に対して | 直した後の粗利率 |
|---|---:|---:|---:|
| ノードの 3 行が重複（区間を残す） | 2,647,672.00 USD | 3.92% | 90.746%（+0.378 pt） |
| 区間の 3 行が重複（ノードを残す） | 4,508,514.20 USD | 6.68% | 91.011%（+0.643 pt） |

製品別：`SmartXPro_IN` は費用の 7.9%（ノード）／13.5%（区間）、粗利率 87.39% → 88.39%／89.09%。`SmartXPro_CN` は 9.5%／16.1%、89.76% → 90.73%／91.41%。「一部だけ重複」なら、この範囲の内側。

単位：**取り違えは無い。** このモデルは 1 lot ＝ 1 台で、明細の `qty` の合計 708,537 は `total_qty_units` と一致する。`basis=per_lot` の表記と備考「per lot (100 units)」は古い名残で、金額は 1 台当たり。ノードと区間は同じ倍率で直され、同じ `qty` を掛けている。

直した場合に変わるもの：`tests/golden/smartx-2027-2029.json` の `ppc` の部分（費用・粗利・粗利率。計画の PSI は変わらない）。関税は移転価格が基準なので変わらない見込み。ほかの golden は変わらない。smartx の PPC の金額を期待値に持つテストがほかにあるかは確かめていない（直すときに full で確かめる）。

## 5. 依頼の外で見つけたこと：SmartX・SmartXNext の区間の運賃と関税は引かれていない

`ppc_edge_cost_rule.csv` の SmartX・SmartXNext の 8 行と、`ppc_tariff_rule.csv` の同じ 8 行は、鍵が supply point 経由のまま（`AssemblyCN_g1->SP_SmartX`、`SP_SmartX->Retail_AMER_g1` など）で、**明細に 1 行も出ない**（§2 の 2 と同じ状態が残っている。棚卸し #4 の「supply point 起点の区間」は、Value Chain だけでなく PPC でも引かれていない）。

- その結果、兄弟の製品で運賃の計上がそろっていない：SmartXPro は ノード＋区間（AMER 27.0）、SmartX はノードだけ（AMER 9.5）、SmartXNext もノードだけ（10.5）。
- **米州向け 25%・欧州向け 7.5% の関税が、SmartX・SmartXNext では 0 で計上されている。**
- 規模の概算（Pro と同じ付け替えをしたと仮定。区間の運賃 ＝ 明細の物量 × 規則の額、関税 ＝ 明細の移転価格 × 税率）：運賃 約 8,069,860 USD、関税 約 4,084,007 USD、計 約 **12,153,867 USD（今の費用の 18.0%）**。運賃の分は、§2 の問いの答え次第で「引かないのが正しい」にもなる。関税の分は、どちらの答えでも抜けている。
- PPC は、鍵の合わない規則があっても警告を出さない（`ppc_warnings.csv` には価格の開始週の件だけ）。

## 6. 大杉さんに決めてほしいこと

1. **運賃の意味**（§2 の問い）。答えによって直し方が決まる：
   - 同じ輸送 → ノードの 3 行を消す（運賃は区間だけ。Start Here R8 に合う。−2,647,672 USD）。または区間の 3 行を消す（最初の版で計上されていた額に戻る。−4,508,514 USD。ただし運賃がノードに残り、Value Chain の読み込みで止まる）
   - 一部が別の費用 → ノードの行を、運賃を除いた額にして費目を分ける（港湾取扱・通関。額は大杉さんが決める）
   - 全部が別の費用 → 金額はそのまま、ノードの備考と費目だけ直す
2. **SmartX・SmartXNext の扱い**（§5）。Pro と同じ規則にそろえるか（区間の運賃・関税の鍵を実在の区間に付け替える。1 と同じ判断を 6 か所にも当てる）。3 組だけ直すと、兄弟の製品との不ぞろいが残る。
3. **golden を作り直すか**。1・2 のどれを選んでも smartx の golden の `ppc` が変わる。1 と 2 を一度に直して 1 回で作り直すのがよいと考える。
4. AMER のノードの備考「CN→AMER」（製品はインド組立）は、行を残すなら直す。
