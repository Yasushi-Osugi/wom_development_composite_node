# WOM 業務の意味体系（Business Semantics）— 読み方と更新の手順

- 版：v0.1（2026-10-26）
- 担当：Claude君（Knowledge Curator、更新の主担当）。レビュー：GPT君（意味の整合と再利用の条件）。根拠：Code君（実装と実行結果）。判断：大杉さん（Business Semantics Owner）
- 位置づけ：WOM の**業務の意味**を、WOM の実装から切り離して書く場所。新しい人・新しい AI は、機能の名前を探す前に、ここで「業務として何を解くのか」を確かめる。

---

## 1. 三つを分けて書く

| 置き場所 | 書くこと | 書かないこと |
|---|---|---|
| **意味体系**（`docs/semantics/`、この下） | 業務の用語の定義、判断に要る業務の情報、適用の範囲、例題、未決事項 | 関数名・CSV の列名・実行の手順（実装が変わっても、意味は変わらないようにする） |
| **WOM との対応**（`docs/design/` の設計 MD） | 意味ごとに、WOM のどの機能・入力・実行の経路で表すか、実装の前提、根拠の commit | 特定の事例でそろっているか（事例の記録に書く） |
| **事例と証拠**（`requests/`・`docs/development/` の設計書・報告書） | その事例で採った方針、仮定、設定、試行の結果、根拠の版 | 一般の定義（事例だけの条件を一般化しない） |

例：「配分の数量を人が指定するなら、金額の情報が無くても業務の判断はできる」は**意味体系**に書く。「今のハンドオフは配分を明示しても原価の CSV を読む」は**WOM との対応**に書く。「化粧品には原価の CSV が無い」は**事例**に書く。三つを混ぜると、「配分には常に原価が要る」という誤った一般化が生まれる。

## 2. 記述の状態

各文書と、各定義・規則の行に、次のどれかを付ける。

| 状態 | 意味 | 変えてよい人 |
|---|---|---|
| **採用済み** | 大杉さんが業務の方針として決めた | 大杉さんの判断で |
| **提案** | Curator が対話・試行から取り出した。レビュー・判断の前 | Curator（レビューを経て） |
| **未確認** | 根拠がまだ無い（実行していない、出典を確かめていない） | 根拠がそろったら Curator が状態を上げる |
| **未決** | 業務の方針として大杉さんの判断が要る | 大杉さん |

推測で「採用済み」「確認済み」にしない。状態を上げるときは、根拠（判断の日付、実行の ID、commit）を添える。

## 3. 定義の書き方

定義の表には、少なくとも次を持たせる。

| 列 | 中身 |
|---|---|
| 用語 | 業務の言葉（必要なら英語を併記） |
| 定義 | 一文で |
| 対象 | どの需要・どの物か |
| 単位 | lot・個・金額など |
| 時間 | 時点か期間か、どの期間か |
| 決める主体 | 業務の誰が（WOM のどの層かは対応表に書く） |
| 例外・注意 | 混同しやすいこと |
| 状態 | §2 |

あわせて**例題**を置く。例題を説明できるかで、人も AI も用語を理解したかを確かめられる。

## 4. 更新の手順

1. **Curator（Claude君）が更新案を作る**：対話・試行から、定義・業務の方針・実装の事実・未確認事項を分けて取り出す。
2. **Code君が根拠を出す**：入力・呼び出し・出力・実行の結果と、対象の commit。
3. **GPT君がレビューする**：用語の混同（例：配分と納期延期）、事例だけの条件の一般化、根拠と例題を点検する。
4. **新しい業務の方針だけ、大杉さんの判断に戻す**。意味を変えない索引の修正や、確かめ済みの根拠の更新は、Curator が進める。
5. **Curator が正本と索引（Start Here）を更新する**：改訂の理由と適用条件を残し、古い記述には訂正先への案内を付ける。

## 5. 確かめ方

新しいセッションの AI に `docs/WOM_Start_Here.md` だけを渡し、各文書の「確認の問い」に答えてもらう。会話の記録（chatlog）を補わなくても答えられれば、知識の整理が機能している。
