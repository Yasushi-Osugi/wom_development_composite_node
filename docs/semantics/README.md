# WOM 業務の意味体系 読み方と更新の手順

- 版：v0.2（2026-10-26）
- 原案・更新の主担当：Claude君（Knowledge Curator）。v0.2 の改訂案：GPT君（Sol君）
- レビュー：GPT君（意味の整合と再利用の条件）。実装・実行の根拠：Code君。業務上の採用判断：大杉さん（Business Semantics Owner）

ここは、WOMの**業務の意味**を、WOMの実装から切り離して書く場所である。新しい人・新しいAIは、機能名を探す前に、ここで「業務として何を解くのか」を確かめる。

知識を記録するときは、**業務として採用したか**と、**何を根拠に、どこまで確認したか**を別々に記録する。採用した方針でも、対象ケースでの実装や動作が未確認の場合はある。実行して挙動を確認しても、その方針を業務として採用したことにはならない。

## 1 三つを分けて書く

| 置き場所 | 書くこと | 他の場所へ分けること |
|---|---|---|
| **意味体系**（`docs/semantics/`） | 用語の定義、判断に必要な業務情報、対象・単位・時間・適用範囲、例題、未決事項 | 関数名・CSV列名・実行手順はWOMとの対応へ分ける |
| **WOMとの対応**（`docs/design/`の設計MD） | 意味をどの機能・入力・実行経路で表すか、実装上の前提、根拠の版 | 特定ケースの設定・採否・試行結果は事例の記録へ分ける |
| **事例と証拠**（`requests/`・`docs/development/`） | 採用した方針、仮定、設定、試行結果、確認対象の版 | 一般化する定義は意味体系へ戻し、事例固有の条件を付けて残す |

例えば「人が配分数量を指定する場合、金額情報なしでも業務の判断はできる」は意味体系に書く。「現行の配分経路が原価情報を読む」はWOMとの対応に書く。「ある試行では金額が未設定だった」は対象ケースと版を付けて事例に書く。この区別によって、実装の入力依存を、そのまま業務上の必須条件として一般化することを防ぐ。

## 2 採否と根拠の確認状態

### 2.1 採否

採否は、定義・規則・方針を、どの範囲で業務上の前提として使うかを表す。

| 採否 | 意味 | 記録すること |
|---|---|---|
| **提案** | レビューまたは採用判断の前の案 | 提案者、提案理由、確認すべき点 |
| **採用** | 大杉さんが、明示した範囲で採用した定義・方針 | 判断者、判断日、判断記録への参照、適用範囲 |
| **保留** | 判断待ち、または条件が未確定のため採用を決めていない | 未決事項、判断に必要な条件、判断する主体 |
| **廃止** | 撤回・置換等により、今後の前提として使わない | 廃止理由、判断記録、後継の定義・規則への参照 |

GPT君のレビュー完了やCode君の動作確認だけで、採否を自動的に「採用」へ変えない。「採用」は、実装済み・全ケースで検証済みという意味を含まない。

採用した内容の意味を変える場合は、採用済みの版と判断記録を残し、変更案を新しい版の「提案」として扱う。未決事項は、内容と判断条件を記録して保持する。意味を変えない索引修正や根拠の追記は、Curatorが進められる。

### 2.2 根拠の確認状態

根拠の確認状態は、**何を、どの方法で確認したか**を表す。確認結果と対象範囲を必ず添える。

| 確認状態 | 意味 | この記録だけからは判断しないこと |
|---|---|---|
| **未確認** | 当該の主張・動作について、必要な確認をまだ行っていない | 情報が無いことを、機能や業務上の条件が存在しないことと同一視しない |
| **文書確認** | 判断記録・仕様・報告書・出典を読んで、記述を確認した | 文書に書かれた実装・動作を、自分で実行確認したとはしない |
| **コード確認** | 特定の版のコードを読み、処理・入力依存・記録方法を確認した | 実行結果、全条件での成立、業務上の採用を意味しない |
| **実行確認** | 記録した入力・設定・環境で実行し、挙動を確認した | 未実施のケースや条件まで成立すると一般化しない |

「文書確認」は、業務方針や定義の出典を記録するために用いる。実装を伴わない定義に、コード確認や実行確認を一律に要求しない。

これらは一つの順位ではない。文書・コード・実行の確認記録を併存させ、過去の記録を最後の確認状態だけで上書きしない。同じ項目でも、コードの入力依存は確認済みで、対象ケースの動作は未確認という場合がある。

**実行確認は、合格という意味ではない。** 適合した結果、不適合・不具合を確認した結果、判定できなかった結果を区別する。コード確認でも、意図との不整合を見つけた場合は、その内容を残す。

根拠の記録には、少なくとも次を含める。

- 確認対象：どの定義・規則・実装上の主張を確認したか
- 確認状態と結果：文書確認・コード確認・実行確認等と、分かったこと
- 担当者と確認日
- 根拠：判断記録、出典、コードのcommit、実行ID、報告書等への参照
- 適用範囲：対象ケース、入力・設定の版、対象SKU・期間・条件。実行した場合は環境も記録する
- 限界：未確認の条件、未実施の検証、残った疑問

実装の詳しい根拠はWOM対応表、実行の詳しい根拠は事例の報告書に置く。意味体系側は、その記録への参照を持つ。

### 2.3 二つの軸の読み方

以下は状態の説明例であり、今回の知識を実際に採用・実行確認したことを示す表ではない。

| 状況の例 | 採否 | 確認対象と根拠の確認状態 | 読み方 |
|---|---|---|---|
| 方針は採用したが、対象ケースでの動作は未調査 | 採用 | 対象ケースの動作：未確認 | 業務上の意思と、実装・動作の確認は別である |
| 改善案の根拠になる入力依存をコードで確認した | 提案 | 入力依存：コード確認 | 根拠はあるが、改善案の採用や動作確認は済んでいない |
| 未配分需要の扱いを判断記録上も保留している | 保留 | 未決事項の記録：文書確認 | 根拠があっても、業務方針が決まっているとは限らない |
| 反例を実行して確認し、旧規則を撤回した | 廃止 | 旧規則の反例：実行確認（不適合） | 確認記録は旧規則の成立を示すものではなく、撤回の根拠になる |

## 3 定義の書き方

定義の表には、少なくとも次を持たせる。

| 列 | 中身 |
|---|---|
| 識別子・用語 | 文書IDと用語・規則を特定する参照。必要なら英語も併記する |
| 定義 | 一文で示す業務上の意味 |
| 対象 | どの需要・物・主体を扱うか |
| 単位 | lot・個・金額等。集計するときにそろえる単位 |
| 時間 | 時点か期間か。要求期間・判定時点・イベントのどれかを明記する |
| 決める主体 | 業務の誰が判断するか。WOMの層・処理との対応は対応表に書く |
| 例外・注意 | 適用できない範囲、混同しやすいこと |
| 採否 | §2.1の値と、判断記録への参照 |
| 根拠の参照 | §2.2の確認記録への参照。確認状態・結果・範囲を辿れるようにする |

あわせて例題と確認の問いを置く。数量式には、対象とする需要集合、単位、判定時点、成立する条件を付ける。例題の計算が一致することと、実装がその量を正しく観測できることは、別々に確認する。

文書全体の既定の採否を置く場合は、個別項目の例外を明記する。未記入の欄を「採用」や「実行確認」と解釈しない。根拠は原則として、確認した項目ごとに記録する。

## 4 更新の手順

1. **Curatorが更新案を作る**：対話・試行から、定義・業務方針・実装上の事実・未確認事項を分ける。意味を変える案には「提案」と適用範囲を付ける。
2. **根拠を整理する**：Code君等が、コード確認と実行確認を区別して記録する。業務の定義・方針は、大杉さんの判断記録や出典に結び付ける。未実施の確認は未実施と書く。
3. **レビューする**：用語の混同、事例条件の過度な一般化、例題、実装との対応、根拠の範囲を点検する。GPT君が改訂案を作成した場合（v0.2）も、作成とレビューを区別して扱う。
4. **採否と根拠を別々に更新する**：新しい定義・業務方針の採用は、大杉さんの判断記録を付ける。根拠を追加しただけで採否を変えない。採用判断だけで確認状態を実行確認にしない。
5. **正本と索引を更新する**：Curatorが改訂理由と適用条件を残し、Start Hereと文書一覧の表示をそろえる。意味を変えない索引修正や確認済み根拠の追記は、その範囲で進める。旧版・廃止項目には後継への案内を付ける。

対象コード・設定が変わった場合も、過去の確認記録は、その版に対する証拠として残す。最新版への適用は差分を確認し、必要な範囲で新しい確認記録を追加する。

### 4.1 Start Hereでの表示

採用判断前の意味体系は、例えば次のように表示する。

> 供給配分の意味体系（採否：提案。根拠の確認範囲は各項目の記録を参照）

採用後も、実装や対象ケースの確認が未実施なら、その点を分かるようにする。一つの確認結果を文書全体やすべての機能へ広げて表示しない。

## 5 確かめ方

新しいセッションのAIに[WOM Start Here](../WOM_Start_Here.md)だけを渡し、意味体系の文書と、その先のWOM対応表・事例の根拠へ辿ってもらう。chatlogを補わなくても、定義と適用条件を説明できるかを見る。

少なくとも次を確認する。

- 「採用」と「実装・動作の確認」を分けて説明できるか。
- 「実行確認」に、不適合を確認した結果も含まれることを説明できるか。
- 個々の定義や規則について、判断者・適用範囲・根拠の版を辿れるか。
- 供給配分の例題で、元需要・配分済み需要・未配分・実納品・期末未充足を区別できるか。

リンク先の存在確認、数量例の計算確認、コード確認、新規AIによる読解確認、シミュレーションの実行確認は、それぞれ別の確認記録にする。

## 7 旧版からの移行

| 旧版の状態 | 新しい記録への移し方 |
|---|---|
| 採用済み | 採否は「採用」。既存の判断記録を保持する。根拠の確認状態は、実際の記録から別に設定する |
| 提案 | 採否は「提案」。文書・コード・実行の確認がある場合は、それぞれの根拠を付ける |
| 未確認 | 根拠の確認状態に「未確認」を記録する。採否はこの語から推測せず、元の判断記録を確認する |
| 未決 | 採否は判断待ちとして「保留」。未決事項と判断条件を残す。根拠の有無は別に記録する |

既存の`status`欄を移行する場合は、採否を表す欄と根拠への参照に分ける。例えば`adoption_status: 提案`と`evidence_refs: []`を用いることができる。根拠の参照が空なら、確認済みと解釈しない。これらはMarkdown上の記録形式の例であり、現行エンジンが自動処理する設定を追加したものではない。
