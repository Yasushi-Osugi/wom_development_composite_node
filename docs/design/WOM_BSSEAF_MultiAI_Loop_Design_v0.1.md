## 0. 何を自動化し、何を自動化しないか

化粧品の事例（最初の基準事例）では、大杉さんが AI の間の橋渡しをした：依頼を渡す、結果を共有する、指摘を設計へ戻す、採用した内容を知識へ反映する、git の操作。一方、**内側のループ**（Code君が依頼書の中で実装 → テスト → 修正を回し、止める理由で止まる）は、既に半ば自律的に回っている。

| 自動化の対象 | 自動化しないもの |
|---|---|
| 成果物の受け渡し、作業の状態の管理、次の担当の選択、受入条件との機械的な照合、決めた範囲の中の修正の往復、知識の更新の**候補**の保存 | 業務の目的・価値の基準・許容の範囲・重要な変更の採否（段階 5）、新しい意味・例外の確定、知識の**採用** |

自動ループの中心は「次に何を試すか」だけではなく、**「今の知識を、この条件で使ってよいか」**を判断することにある。定められたモデルの中でのパラメータの探索（数値の探索）も、ループの中で使えるが、それを**どの業務の意味と条件の下で**行うかまでを扱う点が、従来の探索の支援と違う。

## 1. 役割と入出力

| 役割 | 入力 | 出力 | 例 |
|---|---|---|---|
| 設計 AI | 業務の要件、Owner の方針と受入条件、知識ベース（Start Here から） | 使う知識・版・適用条件、試行の依頼（依頼書）、知識が見つからないときの調査・提案 | Claude君 |
| 実装 AI | 依頼書、対象の commit、モデル | 隔離した環境での試行の結果、報告書、根拠のファイル | Code君 |
| 検証の担当 | 共通の材料（進め方の知識 §3.3：業務の要件・採用済みの意味と制約、入力・commit・知識の版、成果物と受入条件）。設計者の推論の履歴は渡さない | 独立に読み取り・再計算・再実行したことの記録、受入条件との照合の結果 | 別系統の AI、新しいセッション、CLI・テスト・golden |
| 人（Owner） | 選択肢と影響、知識の更新の候補 | 判断（採否）、範囲の設定 | 大杉さん |
| 制御処理 | 引き継ぎの記録（§2） | 次の担当の選択、停止・再開、人への差し戻し | 未実装 |

正しさの確認は、できるだけ**実行できる確認**に寄せる：CSV の実行結果、数量の関係（①＝②＋③、②＝④＋⑤）、Lot_ID の照合、golden、冪等。

## 2. 共通の引き継ぎの形式

依頼書・報告書の冒頭に、機械でも読める欄（YAML）を置く。この文書が形式の正本で、各依頼書・報告書は具体の値を書く。三層設計 MD の先頭の `knowledge_id`・`evidence_commit` の欄が先例。

```yaml
handoff:
  case_id: BSSEAF-COS-U4          # 案件
  task_id: U4-T1                  # 作業
  role_from: design               # design / implement / verify / owner
  role_to: implement
  target_commit: <sha>            # 対象の版
  knowledge_used:                 # 使った知識と適用条件
    - id: WOM-SEM-SUPPLY-ALLOCATION-001
      version: v0.3
      applicability: "化粧品の事例、identity、数量配分モード"
  acceptance:                     # 受入条件（依頼書の節を指す）
    ref: requests/<依頼書>.md#受入条件
  evidence:                       # 実行の結果・根拠のファイル
    - docs/development/<報告書>.md
  status: 試行可能                 # §3 の作業の状態
  open_items:                     # 未決事項
    - "端数の同順位の規則（Owner の判断待ち）"
  stop_reasons: []                # 止める理由（あれば）
  handover_notes: []              # 申し送り
  next: verify                    # 次の担当、または owner
```

- 「完了」と書いたことには、**受入条件を満たした証拠**（`evidence`）を結びつける。YAML の記述と実行の結果を照合できるようにする。
- 作業の「完了」と、知識の「採用」「実行確認」は**別の状態**として扱う（知識の採否と根拠は `docs/semantics/README.md` §2 の二軸）。

## 3. 作業の状態と遷移

| 状態 | 意味 | 次へ進む条件 | 人へ戻す条件 |
|---|---|---|---|
| 調査中 | 知識・実装を、決めた範囲で調べている（進め方の知識 §3.2 の表の 1 行目） | 条件の合う知識を確かめた → 試行可能 | 業務の前提に関わる知識が無い → Owner 判断待ち |
| 提案作成中 | 定義・適用条件・確認の方法を「提案」として作っている（同 2 行目） | 提案を作った → Owner 判断待ち（採否） | — |
| 試行可能 | 使う知識・受入条件・変更を許す範囲が固定された | 実装 AI が着手 → 試行中 | — |
| 試行中 | 隔離した環境で試行している | 結果と証拠がそろった → 検証中 | 止める理由に当たり、範囲の中で直せない → 修正待ち／Owner 判断待ち |
| 検証中 | 検証の担当が照合している | 受入条件を満たす → 完了 | 受入条件と食い違う → 修正待ち |
| 修正待ち | 範囲の中の修正を返した | 修正した → 試行中 | 反復の上限に達した → Owner 判断待ち |
| Owner 判断待ち | 選択肢と影響を整理して人へ戻した | 判断が出た → 試行可能 等 | — |
| 完了 | 受入条件を満たした証拠が結びついた | 知識の更新の候補を保存 → §5 | — |

**実行中に固定するもの**：目的、受入条件、変更を許す範囲、知識の版、入力。各担当が同じ版を使う。

**計画の結果と不整合を分ける**（意味体系の区別を引き継ぐ）：⑤ 配分後の未充足が残ることは**計画の結果**として記録し、止めない。入力や数量の不整合（関係式が成り立たない、期間・能力の固定が破れる、golden が意図せず変わる）は**止める理由**。

## 4. 停止と再開

- **反復の上限**：修正の往復の回数・時間の上限（値は U4 で決める。例：修正待ち → 試行中を 3 回）。上限に達したら Owner 判断待ちへ。
- **知識が見つからない**：未確認の知識を適用した実行は止める。調査と提案は続けてよい（進め方の知識 §3.2）。
- **新しい意味・例外・未決の方針**：Owner 判断待ちへ。
- **再開**：Owner の判断を引き継ぎの記録に書き、状態を戻す。判断の番号（D・J・M・U）を付ける。

## 5. 知識の更新の候補を正本へ戻す

1. 完了した作業から、知識の更新の候補（新しい定義・適用条件・索引の直し・落とし穴）を、根拠と一緒に保存する（採否：提案）。
2. 戻す先を内容で決める：業務の意味 → `docs/semantics/`、仕事の進め方 → `docs/bsseaf/`、制御・受け渡しの問題 → この文書、WOM の機能との対応 → `docs/design/` の設計 MD、事例の証拠 → `docs/development/`。
3. レビューを経て、Owner が採否を決める。Curator（Claude君）が正本と Start Here の索引を直す。

## 6. 前提と注意

- **データの扱い**：WOM は企業の機密情報を扱うため、Stand Alone の Windows PC が前提である。実企業のデータで自動ループを回すとき、クラウドの AI に何を渡すかは別の設計の論点になる。架空の事例（化粧品など）では問題ない。
- **独立性**：設計・実装・検証が同じ系統のモデルで文脈を共有すると、同じ思い込みで通りやすい。検証は実行できる確認に寄せ、レビューは別系統の AI か文脈を渡さない新しいセッションにし、事前の関与と受け取った文脈を記録する（進め方の知識 §3.3）。

## 7. U4 での小さな試し方

大杉さんが配分の方針と受入条件を決めた後に、次の往復を試す：

1. 設計 AI が、使う知識と適用条件を示す（§2 の `knowledge_used`）。
2. 実装 AI が、週別の配分を作って試行する。
3. 検証の担当が、数量・期間・能力・年齢を照合する。
4. 範囲の中の修正を返し、結果と知識の更新の候補を残す。

測ること：人の橋渡しの回数と中身（転記・連絡／git の操作／業務の判断／レビューへの対応）、根拠が欠けずに引き継がれたか、要る場面で人へ判断が戻ったか。

この段階では制御処理は作らず、§2 の引き継ぎの欄を人と AI が書いて回す（形式の試し）。結果を見て、制御処理を具体化する。
