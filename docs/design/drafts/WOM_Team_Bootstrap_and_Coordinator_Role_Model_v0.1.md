## 1. 結論と問題意識

WOM開発を「今のメンバーだから開発できる」状態から、「蓄積した知識を読めば、新しいメンバーでも開発を継続できる」状態へ進める。

そのために、次の二つを一体として整備する。

1. **チームの復元・起動手順**：新しいAIが、WOMの目的・業務知識・自身の役割・現在地・次の仕事を、版の明確な資料から把握する。
2. **WOM開発コーディネーター**：人間への判断材料の提示と、AI間の定型的な受け渡し・進行管理を担う、AI側の対話窓口を置く。

現在、大杉さんはオーナーとしての意思決定に加え、作業の進捗確認、次の担当の選択、Request Letterや設計書の添付、リポジトリ上の場所の指定、着手指示を行っている。この定型的な橋渡しを減らし、目的・価値基準・採否・重要な例外の判断へ集中できるようにする。

役割を定義しただけでは、別サービスのAIを自動起動できない。役割・共有記録・状態管理に加え、各AIへ仕事を渡す接続手段と、起動を継続する実行基盤が必要である。

## 3. 復元性・可搬性・自律性の定義

| 用語 | 本書での意味 |
|---|---|
| 復元性 | 新しいセッションが共有資料から役割・採用済み判断・進行状態を読み取り、適切な次の仕事へ進めること |
| 可搬性 | 役割の責務と成果物の条件を保ったまま、担当AI・モデル・サービス・実行環境を変更できること |
| 自律的な起動 | 事前に定義・承認された開始条件と権限の範囲で、次の担当への受け渡し・着手・追跡を行うこと |
| 人間の意思決定 | 目的、価値基準、採用する業務前提、重要変更、成果の採否、権限の範囲を決めること |

以前のAIと同じ発想・話し方・判断過程の再現は保証しない。復元の合格条件は、同じ意味・制約・採用済み判断に基づいて、担当業務を継続できることである。

## 4. チーム構成と責任分担案

既存の専門5ROLEに、コーディネーターを加える。ROLEは恒常的な責務、担当AIやセッションは交換可能な実行担当として管理する。

| ROLE | 当面の担当イメージ | 主な責務 | 次へ渡すもの |
|---|---|---|---|
| Owner | 大杉さん | 目的・優先順位・採用前提・重要変更・受入の判断 | 判断、理由、適用範囲 |
| Coordinator | 新たな進行管理AI | 対話窓口、現在地の管理、判断材料の編集、受け渡し、起動・追跡 | 判断依頼、担当別作業パッケージ、進行記録 |
| Architect | GPT君 | 全体整合、構想整理、変更範囲の評価、レビュー | 方針・整合性レビュー・設計上の制約 |
| Management Consultant | GPT-MC君 | 経営・業務の意味、前提、期待結果、判断案の定義 | 業務定義、検証例、未決事項 |
| Designer | Claude君 | 業務定義とWOMの対応付け、詳細設計、依頼書作成 | 設計、Request Letter、受入条件 |
| Implementer | Claude Code君 | 指定範囲の実装・設定・実行・テスト | 変更、実行条件、出力、報告書 |
| Market Researcher | Grok君 | 外部市場・需要仮説・競合等の調査、根拠と不確実性の整理 | 出典・調査時点付き調査結果、仮説、適用上の限界 |

検証担当は作業ごとに明示する。別セッションという理由だけで独立とみなさず、設計・定義への事前関与、渡した情報、独自に確認した方法を記録する。コーディネーターは専門家による検証の代わりをしない。

Grokの責務の詳細と、GPT-MCの金額編を超える担当範囲は、正式採用前に既存定義・大杉さんの意図との整合を確認する。

## 5. WOM開発コーディネーターのRole Model

### 5.1 目的

大杉さんが判断すべきことを判断できる形で提示し、その判断と既定の運用規則に従って専門AIの仕事をつなぐ。コーディネーター自身も共有記録から復元できるようにする。

### 5.2 入力と成果物

| 入力 | 成果物 |
|---|---|
| Ownerの目的・判断・承認範囲 | 判断記録、適用対象、次のアクション |
| Start Here、役割定義、正典 | 必要資料の索引、参照版、不足・矛盾の一覧 |
| 作業台帳、依頼書、報告書、レビュー | 現在地、次の担当、開始条件、停止理由 |
| AIの受領・着手・完了通知 | 進行状態の更新、重複・未応答の管理 |
| 未決の業務前提・検証不一致 | 選択肢、推奨理由、影響、Ownerへ戻す判断事項 |

### 5.3 権限と境界

| 行為 | 扱い |
|---|---|
| 資料の収集、現在地の要約、判断材料・引き継ぎ案の作成 | 役割の通常業務 |
| 承認済み手順に従った担当の選択、資料の受け渡し、作業起動 | 接続機能と事前の委任範囲が整った後に実行 |
| 条件不足や不一致のある作業の停止・調査への差し戻し | 理由と再開条件を記録して実行 |
| 新しい業務前提、目的、重要な優先順位の変更 | Ownerへ判断を戻す |
| 業務定義・設計・検証結果の内容変更 | 所定の専門担当へ戻す。要約時に意味を変えない |
| 保護対象Coreの改修、golden更新、commit・push等 | 既存のリポジトリ規則と個別の許可を維持。本書で権限を追加しない |
| 自分への新たな権限付与、未承認提案の採用扱い | 行わない |

### 5.4 大杉さんへの判断提示

判断依頼には「一言の判断事項」「選択肢」「推奨案と理由」「影響・未評価事項」「根拠の版」「採用後の次の担当と作業」を含める。判断不要の受け渡しを、その都度の承認依頼に置き換えない。

例：生産量を上げる費用について、業務定義と設計上の対応確認がそろったら、採用する費用の前提を提示する。採用後はその判断を記録し、既定の権限内で設計担当へ依頼書作成を引き継ぐ。採用の事実と、実装・検証の完了は別に管理する。

## 6. 共有する知識と進行状態

復元に必要なのは、次の三つである。

1. **役割定義**：目的、担当範囲、権限、入出力、受入条件。
2. **業務・設計の知識**：意味、適用条件、採用済み判断、根拠、既存機能、検証方法。
3. **進行状態**：誰が何をどこまで終え、何を待ち、次に何をするか。

会話は検討の場とし、継続に必要な判断と状態は共有場所へ残す。Start Hereは全情報を抱える文書ではなく、上記三つへ案内する入口とする。

### 6.1 配置案（新規作成前に既存資料と統合を検討）

| 配置案 | 内容 |
|---|---|
| `docs/WOM_Start_Here.md` | 共通入口。役割一覧・現在地・起動手順へのリンク |
| `docs/team/` | ROLE一覧、各役割定義、参加・復元手順 |
| `docs/workflow/` | 進行規則、権限、状態遷移、引き継ぎ形式 |
| `docs/workflow/current_work.md` | 作業台帳への索引、現在地の短い要約 |
| `requests/` | 個別の依頼書・受入条件 |
| `docs/development/` | 実装・試行・検証報告 |

初期はMarkdown表とYAML等で管理できる。将来データベースやIssue管理へ移す場合も、正本を一つに定め、可搬な形式で書き出せるようにする。複数の台帳を独立に更新しない。

### 6.2 作業台帳の最小項目

| 項目 | 記録内容 |
|---|---|
| 作業ID・試行番号 | 一意な識別子、再試行を区別する番号 |
| 目的・担当ROLE | 作業の目的と責任担当 |
| 担当実体 | AI・モデル・セッションまたは実行環境 |
| 状態・更新履歴 | 未着手、実行可能、作業中など。誰がいつ変えたか |
| 依存・開始条件 | 必要な成果物、採用判断、先行作業 |
| 参照版 | 入力のSHA、依頼書の版、実際に読んだ版 |
| 入力・成果物 | パス、成果物のSHA、報告書、検証証跡 |
| 判断・未決・停止理由 | 判断者、日付、理由、適用範囲、再開条件 |
| 次の担当・次の行動 | 作業後に何へ進むか |

成果物が依頼元SHAの後に作成された場合、入力SHAと成果物SHAを別に持つ。「latest」という語だけで参照版を記録しない。

## 7. 新しいチームの起動・復元手順案

### 7.1 閉じる前の準備

現担当者が、会話だけの採用済み判断と理由、未解決事項、作業途中の成果物、未コミット・未pushの有無を申し送る。これは既存チャットを破棄する指示ではない。現チームを残して並行試験を行う。

### 7.2 起動の順序

1. **起動情報を与える**：リポジトリ、対象ブランチ、入口、割り当てるROLE、許可された作業範囲、接続先を明示する。AIが自分の役割を推測で選ばない。
2. **アクセスを確認する**：原本の特定箇所・表の値などで読取を確認する。読めない資料は明示し、必要なら同じ版の原本を別経路で渡す。
3. **対象版を確定する**：ブランチ先端を確認し、その作業の入力SHAを固定する。別版を参照した場合は差を記録する。
4. **共通知識とROLEを読む**：Start Hereから正典・役割定義・関連テーマを辿る。全リポジトリを一度に読むことを必須にはしない。
5. **現在地を復元する**：台帳、採用判断、依頼書、報告書を照合し、完了・未決・作業中・次の仕事を説明する。
6. **理解を確認する**：根拠付きの回答と小さな実務課題で確認する。「理解した」という自己申告だけで合格にしない。
7. **開始条件を判定する**：未承認の前提、必要資料の欠落、先行作業の未完了があれば、該当作業を起動せず調査・判断依頼へ進む。
8. **受領を確認して開始する**：担当・作業ID・試行番号を記録し、二重起動を避けて実行する。

### 7.3 初回に回答させる共通の確認事項

- WOMの目的と、自分のROLEの責務・権限は何か。
- 何が完了し、何が進行中・未決・保留なのか。
- 次に行う作業、入力資料、開始条件、受入条件は何か。
- Ownerまたは他ROLEへ戻す判断は何か。
- 読んだファイル・節・SHA、未読資料、矛盾は何か。

試験条件には、過去の会話、永続メモリ、プロジェクト共通知識等を受け取ったかを記録する。新しいチャットであることだけを「予備知識なし」の証拠にしない。

## 8. 自律的な進行の最小ルール案

| 状態 | 意味 | 次へ進む条件 |
|---|---|---|
| 未着手 | 作業を登録した段階 | 目的・担当・依頼書等がそろう |
| 判断待ち | Ownerの判断が必要 | 対象と範囲の明確な判断が記録される |
| 実行可能 | 依存・資料・許可がそろっている | 担当への送付と受領確認 |
| 作業中 | 担当が着手した | 成果物と実行報告の提出 |
| レビュー待ち | 成果物提出済み、受入は未確定 | 指定担当の検証・レビュー |
| 修正待ち | 受入条件に満たない点がある | 修正範囲を明示して再実行可能へ戻す |
| 完了 | 所定の検証・必要な採否が済んだ | 成果物・判断を次の作業へ引き継ぐ |
| 停止 | 接続障害、矛盾、範囲外など | 停止理由が解消し、再開条件を満たす |

判断不要の作業は判断待ちを通らなくてよい。すべての作業に新たなOwner承認を要求する設計にはしない。どの変更・受入に判断が必要かは、既存規則と委任範囲で決める。

受け渡しでは、作業ID・試行番号・担当・入力SHA・依頼書・成果物形式・受入条件・停止条件を渡す。送付、受領、着手、完了を区別する。

再送前には、同じ作業が受領・着手済みかを照合する。応答がないことだけを理由に、新しい担当を同時起動しない。中断から復元したコーディネーターは、既存の実行状態を確認してから再開する。タイムアウト、再試行上限、競合時の優先権は詳細設計で定める。

## 9. ROLEと接続・実行基盤の分離

| 層 | 役割 |
|---|---|
| 対話・判断支援 | コーディネーターが状況と判断材料を分かりやすく提示する |
| 共有記録・進行規則 | 役割、作業状態、依存、版、判断、受入条件を保持する |
| 接続・実行基盤 | 担当AIへの送付・起動、受領確認、結果回収、再開を実行する |

接続方式の候補はAPI、各AIの実行環境、利用可能な連携機能、必要に応じてRPA・画面操作である。本書では各サービスの対応可否、契約、認証、費用を調査・確定していない。

チャット上のROLE定義は、常時稼働や自動監視を実現するものではない。何を契機に実行基盤が起動するか（人の開始指示、成果物の登録、定期確認等）を別途決める。接続先が使えない場合も、引き継ぎ一式を人が転送できる形で保持する。

## 10. 段階的な導入と検証

| 段階 | 実施内容 | 合格の観点 |
|---|---|---|
| 0：知識と現在地の整備 | 既存自動ループ設計との照合、5ROLEとCoordinatorの整理、申し送り、入口更新 | 役割と現在地へ入口から辿れる |
| 1：人が転送する窓口運用 | Coordinatorが判断材料と次の引き継ぎ一式を用意。転送・起動は大杉さん | 資料探しや指示文作成の負担が減り、誤配・前提漏れがない |
| 2：一つの受け渡しを自動化 | 承認済み依頼書から実装担当へ渡し、報告をレビュー待ちにする等 | 受領確認、中断復元、重複防止が働く |
| 3：専門ROLEへ展開 | 業務定義、設計、実装、検証、差し戻しを接続する | 責任と根拠を追跡でき、重要判断をOwnerへ戻せる |
| 4：チーム復元・可搬性試験 | Coordinatorと専門担当を新しいセッション・別環境へ順次交代する | 補足会話への依存を記録し、所定の業務を継続できる |

### 10.1 最初の試験案

既存チームを残し、対象SHAと小さな作業を固定する。新しいCoordinatorに入口と共有記録だけを渡し、次の担当、入力、開始条件、Ownerの判断事項を説明させる。次に一つの仕事を引き継ぎ、途中でCoordinatorを交代させる。

合格の最低条件：

- 既存の採用済み判断を、根拠なく未決へ戻したり変更したりしない。
- 進行中・完了済みの仕事を重複起動しない。
- 未承認の前提を実装指示に使わない。
- 原本を読めない場合に、その事実を正しく報告する。
- 次の担当が、目的・範囲・入力・受入条件を根拠付きで把握できる。
- 中断後に、共有記録から同じ作業状態と次のアクションを復元できる。

### 10.2 測定項目

復元に要した時間、Ownerによる補足回数、定型的な転送・起動回数、判断待ち時間、誤った受け渡し、重複起動、完了後の不具合を記録する。削減率を先に成果として宣言せず、同程度の作業で比較する。人間の判断回数の少なさだけを成功指標にしない。

## 11. 次に決めること

| 判断事項 | 推奨案 | 理由 |
|---|---|---|
| Coordinatorの位置づけ | 専門5ROLEに加える独立ROLEとする | 進行管理の責務と、専門判断の責務を明確にする |
| 最初の対象 | 一つの小さな受け渡しから始める | 状態管理と復元を観察しやすい |
| 進行状態の正本 | 初期はリポジトリ上の台帳を候補とし、既存設計と統合する | 既存の知識蓄積を再利用できる |
| 自動実行範囲 | 採用済み手順の受け渡し・追跡から始める | Ownerの判断を保ちつつ定型作業を減らせる |
| 現チームの扱い | 復元試験が済むまで保持する | 会話だけに残った情報を補完できる |

本書作成は、これらの提案の正式採用や、AI間送信・実行の許可を意味しない。次の設計作業では、既存の自動ループ設計と照合し、最小の試行依頼書へ落とし込む。
