# WOM Rice Seasonal Model — 設計・独立試作 v0.1

- 基準: `26a1e8eb7bc2f899246168a60c8f480857a0b614`。
- 位置づけ: 大杉さんの依頼による「1需要IDの手計算 → 上位能力層の独立試作 → Code君への依頼」の成果。通常Riceへの移行・業務値の確定は含まない。
- 前提: Lot_IDは最終需要の識別子。玄米と精米は同じ物理量ではない。市場の要求週・IDを変えない。

## 1. 一つの需要を先に定義する

`Koshihikari:KANSAI:2027-W01:00001` を一つだけ使う。経路とLTは現行RiceのKANSAI経路から取る。需要の数量1 lotに対する精米10 kg、歩留まり0.9、貯蔵上限などは**検算用の仮定**であり、現行CSVの単位または業務上の合意値とは扱わない。

| 出来事 | 週 | 扱い |
|---|---|---|
| 収穫 | 2026-W43 | 同じ需要IDに玄米 `100/9 kg` を割り当てる |
| 集荷・引渡し | 2026-W44 | 田→集荷LT 1週。供給点は仮想で物理在庫なし |
| 玄米倉庫に入庫 | 2026-W45 | 集荷→倉庫LT 1週 |
| 玄米倉庫から払出し | 2026-W50 | 倉庫→精米LT 2週 |
| 精米 | 2026-W52 | 玄米 `100/9 kg` → 精米 `10 kg` + その他の産出 `10/9 kg` |
| DC入庫・出荷 | 2026-W53 | 精米→DC LT 1週。2026年はISO W53を含む |
| 市場の要求・実出荷 | 2027-W01 | DC→市場LT 1週 |

玄米倉庫の期末IはW45〜W49の5週で1需要lot相当、`100/9 kg`。W50に倉庫Iから抜け、W50〜W51は精米への輸送中。精米在庫と玄米在庫の両方へ同じ原価・物量を残さない。

## 2. 独立した二つの週を選ぶ

既存の `SerialLineAdapter` は市場側の内部計画週を一つ選び、全経路をまとめて前倒しする。Riceでは、収穫週 `h` と精米週 `p` を別々に選ぶ。

- 倉庫到着 `a = h + 田→集荷LT + 集荷→倉庫LT`。
- 倉庫払出し `b = p - 倉庫→精米LT`。
- `a <= b`、精米・DC・市場到着が要求週までに成立すること。
- 玄米Iの期末占有は半開区間 `[a, b)`。輸送中は倉庫Iと区別する。
- 倉庫の能力制約は、週内の「前週末I＋今週P、払出し前」を上限にするため `[a,b]` を予約する。期末Iだけを倉庫の最大占有と呼ばない。週内の到着・払出し順を細分化しない保守的な規則。
- 収穫への遡及窓、玄米貯蔵期間、精米の前倒し許容量を別のパラメータにする。17/26週をRiceに黙って適用しない。
- 非収穫週を収穫候補にしない。週能力と年産収穫量の上限を別々に予約する。
- 能力0はゼロ、Noneは明示した未設定、欠けた設定はエラー。空き週を無制限にしない。

## 3. 資源と単位

`wom/capacity_layer/solver.py` の Request / Option / Problem と検証関数を使う。各候補は収穫・集荷・倉庫受入れ・玄米保管・精米の玄米kg、DC・市場の精米kgを予約する。共有設備は**明示したresource_id**で一つの制約にする。品目ごとの能力表を合算して共有設備能力と呼ばない。

一つの最終需要lotに必要な玄米は `精米kg / 歩留まり`。物量台帳はFractionで検算し、最適化にはfloat係数を渡す。PSIのID件数は最終需要lot相当であり、kg台帳ではない。現行CSVの「lot」とkgとの換算は別途合意が必要。

## 4. 解法と不足

貪欲法と既存LPの比較に加え、試作では整数の需要IDを割り当てるHiGHS MILPを使う。LPが0.5 IDを返しても、0.5のlotを出荷しない。

優先順は (1) 要求週までの整数ID割当数を最大、(2) 精米前倒しlot週を最小、(3) 玄米kg週を最小。市場の利益優先は今回含めない。未割当IDは原要求のまま残す。最適性の証明は指定された候補・資源・目的関数の範囲に限る。

## 5. エンジンとの接続境界

試作は新しい `rice_trial.py` から、隔離した検算用木の内部Demand S/Pだけを書き換える。Source Pは収穫週、田・集荷のSは先送り週、倉庫Sは精米に向けた払出し週、精米・DCのSは処理/出荷週、市場Sは元の要求週。Forwardはidentityで実出荷・I・COを独立に求める。

この経路では既存Forwardの変更を必要としないかを実測する。保護対象core、元Rice CSV、HarvestBatch、golden、プラグイン登録は変更しない。yieldをForwardに新実装したと主張せず、需要lot相当PSIと段階別物量台帳を照合する。

## 6. 本実装へ渡す未決事項

収穫量・貯蔵能力・精米の歩留まり/副産物・鮮度・共有設備・玄米と精米の単価/原価・報告開始・品質年齢・過年度実績をOwner/Claude君と定義する。過年度需要を増やすだけでは将来需要の収穫割当は生まれない。将来のIDを過去収穫へ割り当て、その履歴から報告期首在庫を形成する。

通常RiceとHarvestBatchの切替、golden更新は別の本実装依頼と受入後。`docs/WOM_Start_Here.md` §3/§7 は、確定した業務規則と通常モデルへの受入の状態を同時に更新する。現時点では試作・未確定として追記案を渡す。
