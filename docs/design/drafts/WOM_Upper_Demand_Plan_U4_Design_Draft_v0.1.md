# 上位Demand PlanとU4の接続 設計ドラフト v0.1

**元需要①全体に経営方針を与え、供給条件を考慮して供給対象②を選び、未配分③の理由と実行後の未充足⑤を追跡する。**

本書は、requests/BSSEAF_Cosmetics_AllocationWeekRule_U4_v0.1.mdへ「上位Demand Planの入力・選択方針・出力」を補う設計案である。Demand Priority Allocation構想全体を置き換えず、構想と現行U4の小実験を接続する。[S01][S02]

Claude君には、§3〜§7の設計と既存機能との対応を確認し、§11の追記・修正文をU4資料へ反映してもらいたい。実装範囲と業務方針を定めた後、Code君へのRequest Letterを作成する。

## 1. 現状と今回補うもの

### 1.1 現行U4は数量枠を受け取る週別選択

現行資料は、P2-a2のチャネル別供給対象数量を固定する。元需要①は4,056lot、供給対象②は3,864lot、未配分③は192lotである。A0・A0e・A1で変えるのは、同じ数量枠の中でどの要求週の需要を残すかである。[S01]

この試行は、週別分布と計画結果の関係を調べるものとして有効である。一方、元需要全体の優先度からチャネル間の供給対象数量そのものを選ぶ機能は、今回の試行の前提に含まれていない。

### 1.2 補う上位Demand Plan

上位Demand Planを、次の情報と処理の組として定義する。

1. 元需要と、その出どころ・元の要求週を保持する。
2. External／Internalの根拠から、経営が採用した優先度・Window・最低供給条件を定義する。
3. 数量枠と供給条件の下で供給対象を選び、②③と理由を記録する。
4. Backward／Forwardの実現結果を照合し、必要なら候補計画を改訂する。
5. Ownerが採用した方針・計画・許容した未充足を、根拠とともに残す。

「上位」は、ManagementとしてPSIエンジンへ渡す需要を定める役割を指す。すべてを一度に最適化する新Coreを、この名称だけで必須にしない。

~~~mermaid

  D["元需要①"] --> U["上位Demand Planの選択"]
  P["優先度・Window・最低供給"] --> U
  C["供給条件・数量枠"] --> U
  U --> A["供給対象②"]
  U --> X["未配分③と選択理由"]
  A --> B["Backward・Forward"]
  C --> B
  B --> R["実納品④"]
  B --> F["未充足⑤と原因"]
  F -. "候補計画を改訂" .-> U
~~~

## 2. 需要を捨てずに判断を残す

### 2.1 ①〜⑤の意味を維持する

| 数量 | 意味 | 決まるところ |
|---|---|---|
| ① 元需要 | 対象とする市場・商品・元の要求期間の需要 | 需要シナリオ |
| ② 供給対象 | 元需要のうち今回の供給計画へ渡す部分 | 経営の配分判断 |
| ③ 未配分 | 元需要のうち今回は供給対象に選ばなかった部分 | 配分判断の結果 |
| ④ 実納品 | ②のうち判定時点までに受渡点で引渡しが完了した部分 | Forward等の実行結果 |
| ⑤ 配分後の未充足 | ②のうち判定時点までに引渡しが完了しなかった部分 | 実行結果 |

同じ需要集合・判定時点・単位で、①＝②＋③、②＝④＋⑤を確認する。[S03]

③を「失注」と呼ぶか、予測として対象外にするか、後で繰り越すかはU1の判断である。⑤も、直ちに失注や注文取消を意味しない。納期を変更するならU2の判断を記録する。

### 2.2 capacityから漏れたLotの区別

| 状態 | 扱い |
|---|---|
| 上位で供給対象に選ばなかった | ③として元需要・理由を保持。実行用の需要CSVから除いても、元需要台帳から消さない |
| Backwardで当週能力を超えた | 前の週への押し戻し等の内部配置を追跡する。これだけで③や失注にしない |
| 計画開始より前の調達等が必要になった | past_due_lots等の内部診断を記録し、市場要求と対応付ける |
| Forwardで受渡しが完了しなかった | ⑤として要求Lotと実出荷を照合し、原因を付ける |

現行Backwardの能力処理は、超過Lotを前週へ押し戻し、週0を超える分をpast_dueとして記録する。[S05] 内部のCO・past_due、Capacity Layerの未配置、市場の⑤を同一視しない。

**最初に優先度を与える対象は元需要①全体である。** ②だけへ属性を付ける設計では、なぜ③を外したのかを説明できない。

## 3. 上位Demand Planの入力

### 3.1 元需要と業務方針

| 情報 | 必須の内容 | 定義例・注意 |
|---|---|---|
| 対象 | scenario_id、対象商品・地域・チャネル、計画期間、報告期間 | warmupと営業期間を区別 |
| 元需要 | source_demand_ref、SKU、leaf_out／region、元の要求週、需要量・単位 | 価格変更等で需要量も変える場合は別の需要シナリオ |
| 需要の性質 | 需要予測／確定受注等 | 予測を、顧客と合意した注文と呼ばない |
| 需要区分 | 同じ週・同じチャネル内で優先度が異なる需要群 | 必要な場合のみ。顧客群情報が無いときに推測で分けない |
| External | 季節性、消費時期、商品・地域特性、根拠と適用期間 | 実測、外部出典、実験用仮定を区別 |
| Internal | 重点商品・チャネル、キャンペーン、価格・ブランドの方針 | 4Pの意図を識別。需要増加効果は別仮説 |
| 優先方針 | priority_class、理由、統合規則、policy_id・版 | 初期案は1〜5、1が最優先。番号は倍率ではない |
| 供給サービス条件 | 受渡点、Window、最低供給量・率、同順位規則 | 分母・対象期間・必須か努力目標かを明示 |
| 未配分・納期の扱い | U1、U2の事例での扱い | 未決なら未決として保持し、勝手に繰越しない |

Lot生成前は、元需要の群に属性を持たせてよい。重要なのは全①が対象になり、生成後のLotと対応を追えることである。

### 3.2 供給条件と確認の範囲

工場・設備・週ごとの能力、投入／良品の単位、歩留まり、休業、部材・供給元、輸送LT、在庫方針、製品年齢、計画開始時の状態を入力または既存モデルへの参照として持つ。

能力は期間全体の総量だけで判定しない。要求時期までに利用できる供給、先行生産・保管が許される期間、部材到着と輸送の時間を確認する。累計能力の確認は必要な診断になるが、複数資源・輸送等を含む全体の十分条件とはしない。

化粧品では、登録モデルの規則に従ってwarmup内の先行生産を扱う。比較の途中で、未定義の期首在庫を加えて不足を埋めない。

### 3.3 供給可能の意味

次のどれを目標とするかを方針に持つ。

| 確認基準 | 意味 |
|---|---|
| 要求週どおり | 元の要求週までに受渡しを満たす |
| 指定Window内 | 定義した期間内に満たす。要求週からの遅れの有無も別に記録 |
| 判定時点まで | 遅配を含め、その時点までの受渡しを数える |

判定時点まで届いたことを、販売適期内に届いたことへ読み替えない。Windowが元の要求週と異なる場合、納期変更の判断と、単なる評価上のWindowを区別する。

## 4. 選択方針の二つのモード

| モード | 固定するもの | 選択するもの | 位置付け |
|---|---|---|---|
| **数量枠固定** | SKU×チャネルの②の総量 | その枠でどの要求週・需要区分を残すか | 現行U4の段階A |
| **優先方針と供給条件から選択** | 元需要、経営方針、供給・サービス条件 | チャネル間の数量も含めた②③ | 構想の次段階 |

数量枠固定モードでは、ECの枠を増やして他チャネルを減らす操作は行わない。外部から与えた枠の優先関係と、枠内の週別順位を区別する。

次段階では、②の総量は供給条件と方針を満たす候補から求める。3,864lotを当然の供給可能量として先に固定しない。数量枠や目標量を設けるなら、それが物理上限、販売目標、政策上の枠のどれかを明示する。

同じ「供給可能」という表示でも、単純な能力検査、詳細シミュレーション確認、Ownerの採用を別々に記録する。

## 5. 供給対象を選ぶ手順案

### 5.1 選択と実行を分けた一巡

1. **元需要を固定する。** 対象・単位・元の要求週・需要量を保存し、参照キーを決める。
2. **方針を適用する。** 各需要群に優先度・理由・Window等を付け、数量枠・最低供給・同順位の規則との整合を確認する。
3. **候補②③を作る。** 採用したモードの範囲で供給対象を選ぶ。対象外の量と選択理由も同時に記録する。
4. **Backward／Forwardで計算する。** 指定した能力・LT・在庫等を使い、候補計画の実納品と未充足を求める。
5. **方針に対して照合する。** 量の整合、優先度別の納品、販売適期、最低供給、在庫・年齢、⑤の原因を確認する。
6. **必要なら別候補へ改訂する。** 方針の範囲内で再選択・再配置し、前の版との変更理由を保存する。
7. **採否を判断する。** Ownerが候補とトレードオフを確認し、採用する計画と許容する不足・前提を記録する。

元需要は候補計画を変えても維持する。③を増やして⑤が減った場合は、その変更と逸失した需要を比較表に残す。⑤を結果上③へ付け替えただけで、解決や改善とは扱わない。

### 5.2 優先度と最低供給の関係

選択規則の候補は「必須のサービス条件を守る → 高優先度の充足を先に評価する → 同順位に規則を適用する」とする。必須条件が両立しない場合は、どの条件がどれだけ不足するかをOwnerへ返す。

同順位の規則には、要求週順、需要比例、制約資源当たりの貢献利益等がある。化粧品の既採用U3との優先関係を決め、元の貢献利益基準を黙って置き換えない。[S03]

異なるSKU・設備で能力を融通できない場合、全Lotを一列に並べるだけでは実現可能性を決められない。競合する資源・週と、その使用量を扱う。

### 5.3 高優先が⑤に残った場合

同じ不足資源を競合していた低優先Lotに供給できていないかを調べる。ただし、低優先の納品があるだけで誤配分とは断定しない。

- 資源・週・部材・輸送条件が異なり、代替できなかった。
- Window・期限等で、高優先需要には間に合わなかった。
- 数量枠固定のため、チャネルを越えて選び直せなかった。
- 配置・処理順等が、経営方針を保持していなかった。
- 観測・元需要との対応が不足し、原因をまだ確認できない。

代替可能な候補を再試行する場合、何を選び直したかと結果を残す。条件を変えるなら別シナリオとし、同条件での方針改善と区別する。

### 5.4 自動処理の境界

最初の数量枠固定試行で、上記の改訂ループ全体を自動化する必要はない。まず選択と観測を実行可能にする。

将来、範囲内の候補改訂を自動化する場合は、入力・方針の固定、修正回数・時間の上限、終了条件、Ownerへ戻す条件を依頼書で定める。新しい優先方針や許容遅延をAIが補って続行しない。

| 方針適用表 | 各元需要への優先度・理由・Window・適用規則の対応 |
| 選択台帳 | 元需要ごとの①②③、選んだ／外した理由、適用した数量枠 |
| 実行用需要 | 選択台帳から生成した需要CSVと、その生成条件 |
| Lot対応表 | 元需要群と生成後Lot_IDの対応。③はLot生成前でも台帳に保持 |
| 実行結果 | 元の要求週・実納品週・優先度別の④⑤、納期・Window評価 |
| 診断と判断 | 不足・最低供給違反等の原因、改訂履歴、採否と判断番号 |

CSV／JSON等の具体的なファイル分割は詳細設計で決める。現行配分ファイルはSKU×regionのalloc_lotsであり、上記すべてを表せる確定スキーマではない。[S08]

### 6.2 Lot_IDと元需要の対応

現行ハンドオフは、数量を変更した後にLotを生成する。配分前後・別案のLot_IDが同じとは仮定しない。[S04]

同じ生成後LotのDemand→SupplyではIDの同一性を守る。一方、案どうしの比較は、元需要参照・SKU・leaf_out・元の要求週・需要区分・数量へ戻して照合する。優先度変更のためにID文字列を変えない。

同じ元需要群の一部だけを選ぶ場合、群内が業務上同等であれば数量で対応できる。個別注文の優先が異なる場合には、その区分または安定した個別参照が必要である。CSV行番号だけを業務上の優先順位に使わない。

### 6.3 結果の数え方

①②③は元需要と選択台帳で数える。④⑤は、生成後の市場要求のLot_IDと実出荷を照合し、元需要へ戻して数える。

初回は、化粧品で採用した市場leafの実出荷に対応する受渡点を固定する。別の受渡点を採る場合は、出荷と到着・引渡し完了の違いを扱い、既存の出荷ベースの指標と区別して照合する。

現行Flow Check表2はleaf別・製品別・モデル全体の集計であり、要求週別の行やLot_ID明細を出力する表ではない。[S09] その照合方法を再利用して、次の補助観測を作る。

1. leafの要求Lot_ID→要求週と、実出荷Lot_ID→出荷週を照合する。
2. 元需要・選択台帳との対応から、優先度・元の要求週・Window別に集計する。
3. 集計した②④⑤を、既存Flow Check表2の値と照合する。
4. ①③は元需要・選択台帳から補い、対象外になった週も残す。

実装の候補は既存の木の取得・観測経路を使う補助ツール／観測処理とする。表2のCSVに元から週別明細があると仮定しない。

要求週別の充足と、実納品週別の供給ゼロは別集計である。供給ゼロ週は営業期間・開店前・休業・需要ゼロ週の扱いを明示し、何週も供給が止まるかを測る。

## 7. 時間制約が選択総量へ影響する小さな例

以下は手計算の説明例であり、WOMを実行した結果ではない。

前提：同じSKU、同じ設備、良品能力はW1・W2各5lot。期首在庫0、W1より前の生産なし、LT0、要求週どおりの納品を目標とする。最低供給条件は置かない。

| 元需要群 | 要求週 | 優先度 | ① 元需要 | ② 選択 | ③ 未配分 |
|---|---|---:|---:|---:|---:|
| A | W1 | 1 | 4 | 4 | 0 |
| B | W1 | 5 | 4 | 1 | 3 |
| C | W2 | 3 | 2 | 2 | 0 |
| 合計 | — | — | 10 | 7 | 3 |

期間全体の能力は10lotだが、W1の需要8lotに対する供給は5lotである。W2の余剰3lotをW1へ遡って使うことはできない。要求週どおりに供給できる対象を選ぶと②は7lotとなり、高優先Aを守ってBの3lotを対象外にする。

この前提どおり実行できれば④7・⑤0となる計算だが、実システムでは詳細制約を通した照合が必要である。

遅配を許すなら、Bの残り3lotも②に含めW2に届ける別候補を検討できる。ただし、それは「W1の約束を守った」という結果ではなく、遅配を許す方針との組合せである。

この例は、**期間合計の能力を②へ固定することと、要求時期に間に合う需要を選ぶことが異なる**ことを示す。③と⑤の数を小さくするために、評価する期限を黙って変更しない。

## 8. 現行WOMとの接続と実装候補

### 8.1 現在確認できたこと

| 箇所 | 読取り確認した事実 | 今回の設計への意味 |
|---|---|---|
| handoff.py | SKU×regionの数量を週の元需要へ比例配分し、需要CSVを生成 | 週別選択の差分を置く既存箇所 |
| run_quantity_allocation.py | 数量計画を実行し①〜⑤を記録。PPCは呼ばない | 初回試行の既存経路 |
| bridge_backward() | market_priority引数は受け取るが、処理で使用していない | 引数名だけで優先反映済みとしない |
| Backward能力処理 | Lotリストの先頭を残し、超過を前へ押し戻す | 既存経路は新しい優先属性を直接参照しない |
| Capacity Layer | 適用条件と上位配置の既存機能がある | 再利用可能性を調べる。市場優先・soft条件に自動対応とはしない |
| Flow Check | Lot照合によりleaf等の集計を作る | 週別・優先度別観測へ同じ照合方法を利用できる |

根拠は[S04]〜[S10]。この確認から、優先反映には必ずCore改修が必要とも、道具だけで全要件を満たせるとも断定しない。

### 8.2 比較する実装経路

| 経路 | 対応する仕事 | 次に確認すること |
|---|---|---|
| 上位選択・ハンドオフ・観測 | ①への方針付与、②③の選択、④⑤との照合。必要なら上位で候補を改訂 | 既存引数・データ経路で、週別選択と対応表を安全に渡せるか |
| 既存上位配置の拡張 | 優先需要を資源・週へ配置する | 対象の木、cap_soft／hard、Lot同一性、優先目的への対応 |
| Coreの変更 | エンジン内部で新しい優先属性を使う必要が残る場合 | なぜ上位方式では表せないか、変更箇所、代替案、回帰検証 |

推奨は、まず第一の経路で上位Demand Planの入出力と観測を確立し、必要になった配置上の差分を調査すること。保護対象Coreを変えるなら、別途具体的なRequest Letterと必要な検証を定める。

新しい選択モードを指定しない既存経路は、従来の結果を保つ。行順への依存を解消することで既定の結果が変わり得る場合は、対象と理由を示して扱いを決める。

## 9. 化粧品U4への適用案

### 9.1 最初の範囲

まず数量枠固定モードを使う。P2-a2の元需要①、チャネル別②、合計③、能力・歩留まり・LT・在庫方針・期間・プラグインを固定する。期待する基準再現は①4,056・②3,864・③192・④3,856・⑤8である。[S01][S14]

上位Demand Planの定義として、元需要の性質、今回の数量枠の出どころ、A0・A0e・A1を業務上どう位置付けるかを記載する。

- A0：現在の比例配分と同端数処理の結果を再現する基準。
- A0e：端数の減少を均等に散らす候補。対象期間・重み・位相・決定的な規則を定める。
- A1：早い要求週を残す候補。将来週を外す理由を明示し、確定受注をキャンセルしたとは表現しない。
- 優先度属性・Windowの小実験：必要に応じて追加。化粧品の需要には季節性を置いていないため、実験用の仮定として示す。

A0・A0e・A1の試行だけでは、External／Internalに基づく5段階優先の構想全体を実証したとは扱わない。最初の接続確認と、次段階へ残る差分を報告する。

### 9.2 能力の単位をそろえる

C3aの能力と歩留まり0.97を使う開放週では、次の換算になる。[S06][S11]

| SKU | 投入max_supply | 投入cap_soft | 良品hard上限 | 良品soft配置上限 |
|---|---:|---:|---:|---:|
| COS_Serum | 17 | 14 | 16 | 13 |
| COS_Cream | 13 | 11 | 12 | 10 |

現行softモードのBackward配置は良品soft側を使う。softが全経路における物理的な強制上限という意味ではなく、今回採用した配置条件である。

定常の市場需要17・13lotと比較するなら、良品soft上限との差は4・3lot／週である。現行U4資料の「毎週3・2lot不足」は、投入能力との直接比較なので修正する。

A1の約70・60lotという⑤の概算も、良品換算、LT、在庫方針、実際の生産週、初期状態をそろえて見直す。ここでは新しい⑤の予測値を置かない。

### 9.3 境界の効果と再計画

「再計画するから⑤を業務の欠品と読まない」を前提として確定しない。結果として⑤を保持し、以下の診断を分ける。

- 計画の切り方・期首条件に由来する部分。
- 採用した週別選択により、要求時期までの供給が足りなくなった部分。
- 部材・LT・休業・在庫・期限等による部分。
- 既存の配置方式や処理順の影響が疑われる部分。

分類は根拠に基づき、重なる原因を無理に足し分けない。境界の寄与を調べる期間延長・開始条件変更等は、基準比較と分けた診断試行にする。

再計画による救済を検証する場合は、再計画時点、既に完了した生産・納品、拘束済みの能力、既存注文残、追加される需要、繰越・遅延の扱いを定義する。未来の余剰能力が、過ぎた要求週や販売適期を取り戻したことにはしない。

## 10. 検証と判断

### 10.1 受入候補

| ID | 確認すること |
|---|---|
| UP-V01 | 元需要①と方針の参照が保存され、全需要に方針または明示した適用外理由がある |
| UP-V02 | 元需要群ごとに①＝②＋③、実行後に②＝④＋⑤が成り立つ |
| UP-V03 | 数量枠固定の基準案がP2-a2を再現する |
| UP-V04 | 小さな需要例で、選択と時間制約を手計算に照合する |
| UP-V05 | CSVの行順を変えても、安定した元需要キーに戻した選択結果が同じになる |
| UP-V06 | 生成後Lotの同一性・重複・消失を確認し、案の比較は元需要へ戻して行う |
| UP-V07 | 優先度・要求週・Window別に④⑤を観測し、既存表2へ集計照合する |
| UP-V08 | 高優先未充足・低優先納品の原因を追跡できる |
| UP-V09 | 満たせない必須の最低供給条件を検出し、正常達成と表示しない |
| UP-V10 | 固定条件、入力・規則・知識の版、実行根拠、改訂履歴が保存される |

低優先から高優先への方針変更を比較する場合、元の優先基準での評価も残す。評価ラベルを付け替えただけで、業務成果が改善したようにしない。

### 10.2 結果の状態とOwner判断

「候補作成」「計算済み」「整合確認」「業務目標の達成／未達」「Owner採用」を区別する。計算が完了しても、すべての需要・Window・最低供給を満たしたとは限らない。

入力・対応・数量関係の不整合は停止理由とする。⑤や目標未達は結果として残し、原因と代替案を報告する。Ownerが許容するかどうかと、数値の整合が取れているかを混ぜない。

コードを変える場合は変更範囲に応じた検証を行う。既存goldenが変わったことを隠す再生成は行わない。Coreが必要なら、その差分と検証を具体化する。

## 11. 既存U4資料へ取り込む追記と修正文

以下は、Claude君が編集するための本文案である。節番号は現行v0.1への配置候補を示す。

### 11.1 §1の後へ追加する「上位Demand Planとの関係」

> 上位Demand Planは、元需要①全体について、需要の性質・元の要求週と経営上の優先方針を保持し、供給条件を考慮して供給対象②を選び、未配分③と選択理由を記録する。実行後は④⑤を元需要へ戻して照合し、必要に応じて候補計画を改訂する。
>
> 今回のU4は、そのうち「数量枠固定モード」を試す。SKU×チャネルの②はP2-a2から引き継ぎ、その枠の中でどの要求週の需要を残すかを比較する。チャネル間の総量を経営優先度と供給条件から選び直す処理は次段階とする。
>
> 入力は、元需要、数量枠、週別規則、同順位の扱い、固定した供給条件である。出力は、元需要を残した①②③の選択台帳、実行用需要、生成後Lotとの対応、要求週別の④⑤と原因とする。
>
> 対象外にした③と、供給対象にしたが届かなかった⑤は別に保持する。需要予測を外すこと、確定受注を取り消すこと、後の週へ繰り越すことを同じ意味で扱わない。

### 11.2 §2.3と申し送り欄の修正

> 本試行では、週別規則を②③の選択に直接使用する。現行Backward／Forwardの不足処理は、この新しい優先属性を参照してLotを選び直すものではないため、優先どおりの実納品は保証しない。
>
> 一方、選択した需要分布は配置・供給結果にも影響する。④⑤を元の要求週・適用した方針に対応付け、優先した需要が実際に届いたかと、届かなかった原因を観測する。構想のDP-V07を②の観測だけへ読み替えない。
>
> 優先方針を実現する方法は、上位選択・既存アダプター・上位配置・Core変更を比較して判断する。market_priority引数が未使用であることだけからCore変更を必須とはしない。

### 11.3 §2.2・§4.2の能力と概算の修正

> 能力は投入値と良品lotへ換算した値を併記する。歩留まり0.97の下では、C3aの良品soft配置上限は美容液13・クリーム10lot／週であり、定常の市場需要17・13との差は4・3lotである。
>
> A1の⑤の概算は、この換算とLT・在庫方針・実際の生産週をそろえて見直す。概算値と、実行後に得た結果を区別する。

### 11.4 §4.3・U4-3の修正

> ⑤は計画結果として保持する。計画の境界、週別選択、供給制約、配置方式等の影響を根拠とともに調べる。「再計画するから業務上の欠品ではない」とは事前に確定しない。
>
> 再計画で救済できるという仮説を採る場合は、再計画時点、既実行の活動、繰越・遅延、追加需要等の条件を定義し、別試行で確認する。採用判断は、⑤の数と原因、納期・販売適期・供給継続への影響を見て行う。

### 11.5 §5 M2・M3の出どころの修正

> M2の要求週別①〜⑤は、元需要・選択台帳と、市場要求Lot_ID／実出荷の照合から補助集計する。既存Flow Check表2はleaf等の集計なので、補助集計を表2へ戻して数量照合する。
>
> M3の供給ゼロ週は実納品週で集計し、営業期間・開店前・休業・需要ゼロ週の扱いを明示する。要求週に対する未充足と、実納品が途切れた週を区別する。
