## 1. 段階 D の中心

**「全ノードの利益を足すこと」ではなく、「全ノード・全区間で生まれた価値と内部取引を、同じ Lot の取引記録で追い、Business Owner が見る外部との利益へ、説明付きでつなぐこと」。**

LOVEM の数量の線（どの Lot が、どこから来て、どこで待ち、いつ出荷されたか）に、意味の明確な金額を重ねる。

## 2. 三つの視点（同じ Lot の取引記録でつなぐ）

| 視点 | 答えたい問い | 金額の意味 |
|---|---|---|
| V1 ノード・区間の管理評価 | どの工程・物流区間が価値を生み、費用や在庫を抱えているか | 同じ法人の中の移動も、管理上の内部価格で評価する。大杉さんの原則「全ノードで、実出荷 Lot 数 × Lot 単価」を、ここで守る |
| V2 法人別の損益 | どの会社が、誰に販売し、利益を得ているか | 同じ法人の中の移動（売上にならない）と、他の法人への販売（法人の売上）を区別する |
| V3 グループ全体 | Business Owner から見て、外部との取引でいくら稼いだか | 連結対象の会社の間の取引を消して集約する |

- 同じ Lot_ID が複数のノードを通り、それぞれで売上・原価・利益を持つのは、V1 の正しい姿であり、二重計上ではない。V3 で内部取引を消すことで、グループの外部売上に一致させる。
- **分類の軸は互いに独立**させる：Profit Zone（役割）、法人、国、連結の範囲。1 つの法人が工場・倉庫・販売拠点を持つ場合も、同じ Profit Zone に複数の法人が属する場合も表せるようにする。
- **サプライチェーンの全員が自社グループとは限らない。** Supplier や販売店が外部の場合がある。連結の売上は「最終 leaf の販売」ではなく、**連結の範囲から外部の相手への販売**である。
- **本社**は、集約を見る主体であり、物流のノードとして置く必要はない。

## 3. 用語と定義（草案）

### 3.1 取引の記録（Value Chain Ledger）

基本の単位は、**「ある Lot が、ある週に、ある区間を、ある相手へ渡った」という 1 件の記録**（出荷の事実）。LOVEM の実出荷のイベント（`_actual_ship`）と 1 対 1 に対応させる。

各記録に持たせるもの（案）：

- Lot_ID、製品、数量（lot 数と物量）、出荷ノード、受け手のノード、区間（edge）
- 出荷週・到着週・売上認識週（§3.4）
- 出荷側・受け手側の法人、法人間か法人内か、連結の範囲の内か外か
- 価格の種類（§3.3）と単価、通貨
- 区間の費用（運賃・関税・保険など）とその扱い（§3.5）

### 3.2 法人と連結の範囲

「本社フラグ」だけでは連結の範囲を表せないので、3 つを分ける（Astra君の提案）。

| 表（案） | 内容 |
|---|---|
| 法人の定義 | 法人の ID、名前、機能通貨、国 |
| ノードと法人の対応 | ノード → 法人（外部の相手は「外部」） |
| 連結の範囲 | どの法人を連結に含めるか、報告の主体（本社）、報告通貨 |

### 3.3 価格の三つの種類

| 種類 | 使う場面 |
|---|---|
| 管理評価価格 | 同じ法人の中の移動（V1 だけで使う。法人の売上にならない） |
| 法人間の取引価格（移転価格） | 連結範囲の中の、法人をまたぐ移動（V2 の売上、V3 で消去） |
| 外部市場の価格 | 連結範囲の外への販売（V2・V3 の売上） |

今の PPC の移転価格（`ppc_transfer_price_rule.csv`、工場だけ）は、法人間の取引価格の一部に当たる。区間ごとに、価格の決め方（原価加算・固定・市場価格からの差し引き）を選べるようにする。

### 3.4 計上する週

- **V1（管理評価）は、実出荷の週を基本とする。**
- 会計の売上認識は、たとえば IFRS 15 では「顧客への支配の移転」が基準である。本モデルでは、**「出荷時に支配が移転する」という前提を明示して**、最初の実装を簡潔にする。
- 構造としては、出荷週・到着週・売上認識週を別に持てるようにしておく（取引条件を後で変えられるように）。

### 3.5 区間の費用と在庫原価

運賃・関税などを、発生した週にすべて利益から差し引くとは限らない。IAS 2（棚卸資産）では、物を今の場所と状態にするための費用（仕入の運賃、関税など）は在庫の取得原価に含め、販売したときに費用になる。

区別すること：

- 費用の**発生週**、**負担者**（どの法人・ノードが払うか）、**在庫原価への組入れ**の有無、**売上原価になる週**

これを分けないと、warmup の助走週に仕入れた費用だけが報告期間の外へ落ち、利益を過大に見せるおそれがある（Flow Check・warmup の報告書 §5.5 で、今の PPC は助走週の費用を持たず、原価を販売週にまとめていることが分かっている）。

在庫の保有費用は、まず「Lot・週に応じた管理上の保有費」を独立した項目として用意し、倉庫費や資金費用との重複を防ぐ。

### 3.6 単位と桁の検証（段階 D の入口）

smartphone-global-2026-2029 の PPC の売上 641 兆円は、現実の規模から大きく外れている。原因を「単位の問題」と決めつけず、次の積を 1 つずつ追う。

```
実出荷 lot 数 × 物量／lot（cpu_size など） × 物量当たり単価 × 通貨換算
```

- 単価がすでに lot 単価なら、物量／lot をもう一度掛けてはいけない。
- 部材と完成品で単位が違う。
- 今の PPC は、マスターの単価を「物量（unit）当たり」とし、集計で qty を掛ける約束になっている（`ppc_models.py` の PPCEvent・LotCostAccumulator の説明）。この約束と、各モデルのマスターの値の単位が合っているかを、モデルごとに表にする。

**金額の桁を直す前に、価格・原価それぞれの単位を確定する。**

## 4. 今の PPC・money との関係（要調査）

| 今あるもの | 今の動き（分かっていること） | 段階 D での扱い（案） |
|---|---|---|
| PPC（`wom/ppc/`） | 市場 leaf の販売記録（今は実出荷）を起点に、1 lot ごとに経路を上流へたどって原価を積み上げ、**すべての費用を販売週に計上**する。中間ノードの数量は leaf から導出（P4） | 「製品原価の積み上げ」の見方として残す。V1 の記録（各ノードの実出荷を起点）とは起点が違うので、両者の対応表を作る |
| money（`wom/engine/money.py`） | ノードごとの売上・原価（S2 で実出荷ベース）。中間ノードの売上は 0 のものがある | V1 の記録から作り直すか、V1 と照合する対象にする |
| Profit Zone | ノードの役割ごとの利益の区分 | 分類の軸の 1 つとして残す（法人とは独立） |
| 移転価格 | 工場だけ | 法人間の取引価格の一部として一般化 |

この表の「今の動き」は、段階 D の設計・準備で、Code君に調べてもらう（§6）。

## 5. 最初の数値例（「売れ残り」を必ず入れる）

1 Lot、工場 A の原価 80、販売会社 B への価格 100、B から外部の顧客への価格 150。運賃などは、まず 0 とする。

| 場面 | A の利益 | B の利益 | グループの利益 | グループの在庫 |
|---|---:|---:|---:|---:|
| B が外部へ販売済み | 20 | 50 | 70 | 0 |
| B の在庫に残っている | 20 | 0 | **0**（内部利益 20 を消す） | **80**（B の帳簿は 100） |

この例で、次を 1 つずつ変え、設計の境界を確かめる。

1. A と B が同じ法人か、別の法人か
2. B が連結の範囲の中か、外部の取引先か
3. 当週に売れたか、翌週へ在庫として残ったか
4. 輸送中に週末を迎えたか
5. 生産・仕入が warmup の助走週に発生したか
6. 運賃・関税を入れたとき、在庫原価に入るか、その週の費用か

**この表を、実装の前に大杉さんと手計算で合意する**（完了の条件）。
