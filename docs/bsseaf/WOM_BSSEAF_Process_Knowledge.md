## 2. 誤りの型と打ち手

化粧品の事例の E1〜E5 から。どれも本番のモデルに入る前に、写しの試行か別の担当の確認で止まった。

| 型 | 段階 | 例 | 打ち手 |
|---|---|---|---|
| **前提の外で使った** | 3 | E1：お米の D7 を供給の制約の無い所へ。E2：業務の語 Production_Qty をエンジンの既定 envelope へ。E3：需要の単位 Lot_ID を物の個体へ | 知識に**適用条件**（いつ成り立つか）を付けて残す。Mapping の表で「守れる」に見えても、写しで動かして確かめる |
| **見つけられなかった** | 2 | E4：三層の配分経路が既にあったのに「Core の課題」とした | **索引**。業務の問いから意味体系 → 設計 MD → 事例へ辿る導線を Start Here に置く（Start Here §0.1）。新しい読み手で読解試験をする |
| **確かめる前に前提にした** | 3 | E5：Value Chain が売上の率の費用・MDF を扱えると確かめずに依頼書を書いた | 依頼書の「先に確かめること」を、置き方を決める**前に**設計者がコードを読んで確かめる |

注意：知識が増えるほど「見つけられなかった」型が増えるおそれがある。索引の設計は、回数が増えるほど中心の課題になる。

採否：採用（大杉さん、2026-10-30、検証報告）。根拠：文書確認（化粧品設計書 v0.5 §8.2・§8.3・§8.5、検証報告 第3章）。一つの事例からの型分けで、別の事例では未確認。

## 3. 標準にするもの

### 3.1 BS-SEAF で重点を置く標準：「知識 × 適用条件 × 根拠」

製造の現場の改善活動では、同じ形で繰り返す作業の**手順**の標準化が中心になる。BS-SEAF の一巡は、毎回業務も問いも違う知識労働なので、同じ手順で進めても、使った知識の前提が合っていなければ間違える（E1）。そこで BS-SEAF では、作業の手順の標準（§3.2）も使いつつ、**業務の知識と適用条件を、根拠と組にして、AI も参照できる形で明示すること**に重点を置く。

この原則は、この文書の作法そのものにも当てはめる：§3.2 の作法にも、どの場面で使うかの条件を付ける（進め方の知識を別の場面へ持ち出すときの「前提の外での適用」を防ぐため）。

- 意味体系・設計 MD・Start Here は、BS-SEAF にとっての**標準作業票**に当たる。一巡ごとに適用条件を足し、使えない条件が見つかれば書き換える。
- 読解試験は、その標準作業票が新しい担当者に読めるかの確認に当たる。
- 新しい知識は、最初から適用範囲（例：「化粧品の事例で採用、一般則としては保留」）と根拠を付けて残す。

採否：採用（大杉さん、2026-10-31 の対話）。根拠：文書確認（化粧品の事例の E1・E4、読解試験）。

### 3.2 一巡の中の標準の作法

| 作法 | 中身 | 出どころ |
|---|---|---|
| 隔離して試す | Data・Parameter の試行はモデルの写し（`output/`）で行い、標準のサンプルを変えない。Core・道具の改修の試行は、依頼書に従い、隔離した作業の環境（写し、ブランチ等）で行い、テストと golden で既存への影響を確かめる。採用したものだけを段階 6 で適用する | 各依頼書（例：`shelf_life_check` の改修は P2-a の依頼書の Part A） |
| 先に確かめる | 既存の機能の能力・入力依存を、設計の前提にする前にコードで確かめる（E5 の打ち手） | U3 資料 §4 |
| 止める理由と申し送り | 動き・数字・誤読に関わるもの（数が合わない、golden が変わる、冪等にならない等）は**止めて先に直す**。潜在のリスク・改善の余地は記録して先へ進む。些細なものは往復させずに直して報告だけにする | Start Here §6、各依頼書 |
| 数字の扱いを場面で分ける | **まとめの文書**（検証報告・設計書の要約）では、出典の数字を維持して出どころを付け、計算し直さない。**検証**（段階 7、レビュー）では、独立に再計算・照合し、差があれば記録する | 検証報告、GPT君のレビュー（再計算・小さな再現） |
| 採否と根拠の二軸 | 採用したことと、確認したことを分けて記録する | `docs/semantics/README.md` §2 |
| 範囲を書く | 「どの案・どの条件の値か」を付ける（例：0.05% 未満は 3 案について） | 検証報告 v0.2 |

### 3.3 段階 7：独立性と検証したものを分けて書く

| 確認の活動 | 位置づけ | 検証するもの |
|---|---|---|
| 実装者の受入条件・テスト | 自己検証・回帰の確認（独立ではない） | 結果の再現、golden、冪等 |
| 別の AI のレビュー | 実装者以外のレビュー。設計の一部を書いていれば、設計全体からは独立していない | 文書・根拠・コードの読解、再計算。再実行したかを書く |
| 新しいセッションの読解試験 | 索引から知識に辿り着けるか。経緯を渡したかの条件を書き分ける | 到達と読解（計画の数の検証とは別） |
| Owner の GUI での確認 | 実装者以外による、通常の利用の経路での受入 | 読み込み・計画・金額・表示 |

採否：採用（検証報告 v0.2、GPT君のレビューを反映）。根拠：文書確認。

### 3.4 製造の現場の改善活動との対応（理解のための対比）

| 改善活動 | BS-SEAF |
|---|---|
| 課題を選ぶ・現状を調べる・要因を調べる | 段階 1・2・3 |
| 対策を小さく試す・採否を決める | 段階 4（写し）・5（人が選ぶ） |
| 通常の仕事へ適用する・効果を確かめる | 段階 6・7 |
| 標準を更新し、横展開する | 段階 8（お米から化粧品への再利用は横展開。E1 は横展開で前提を確かめなかった失敗） |
| 自働化（異常で止める） | 依頼書の「止める理由」 |
| なぜなぜ分析 | 誤りを型に分け、仕事の進め方に打ち手を打つ（§2） |

違い：改善活動は作業の手順の標準化が中心で、BS-SEAF は、それも使いつつ、業務の知識と適用条件を AI も参照できる形で明示することに重点を置く（§3.1）。また BS-SEAF には二つの改善が重なる：WOM を使って需給・在庫・配分の方法を改善すること、WOM を設計・検証・適用する仕事の進め方を改善すること。化粧品の事例で直接確かめたのは、主に後者である。

採否：提案（大杉さんの問題提起、GPT君・Claude君の整理、2026-10-31）。理解のための対比で、規則ではない。

## 4. 一巡ごとの記録と測ること

各試行の報告書の「BS-SEAF の記録」の表に、次を持たせる。

| 項目 | 中身 |
|---|---|
| 変えたもの | ファイル・行・値の数、手段（Data／Parameter／Core／道具） |
| 再利用した知識 | どの文書から辿ったか（Start Here の節、意味体系、設計 MD、報告書） |
| 誤り | 型（§2）と、見つけたもの |
| 往復の回数 | 依頼書の版の数、止める理由での差し戻しの数 |
| 実作業の時間と待ち時間 | 分けて記録する（どの段階が律速かを測るため） |
| 見込みどおりか | 外れたら、なぜ外れたか |

成果として見るもの：Core を変えずに表せた割合だけを成果にしない（歩留まりのように、意味を正しく表すための Core の改良も成果）。受入の後の不具合と、同じ型の誤りの再発も一緒に見る。

採否：提案（Claude君・GPT君、2026-10-31。U4 の依頼書から試す）。根拠：未確認。

## 5. 中心仮説（BS-SEAF on WOM 仮説）

### 5.1 大杉さんの仮説（構想）

BS-SEAF の 8 段階を、WOM の機能の改良で 100 回ほど繰り返す中で、BS-SEAF のプロセス自体の効率化・自動化が進む。業務の判断や意味体系の再構成を担う新しい AI のメンバー（例：経営コンサルタントの役を担う AI-Management-Consultant君）が加わることで、WOM の適用の可能性が上がり、適用のハードルが下がる。この「自動化された 8 段階」を 1,000〜10,000 回繰り返す中で、WOM がビジネスとして立ち上がる。そして、地球上の Global Operation と経済活動の効率を最適化するシミュレーションを可能にし、持続可能性を高める。

採否：採用（開発を方向づける中心仮説として。大杉さん、2026-10-31）。根拠：一巡（化粧品）のみ。回数は構想の規模を表すもので、成功の条件は反復の**中身**（新しい業務・制約・利用者に対して前の知識がどこまで役立ったか）に置く。

### 5.2 当面の検証仮説

> **検証の結果と適用条件を伴う知識を、次の事例で再利用することで、品質を保ちながら、WOM の適用に要る手間を減らせる。**

採否：提案（GPT君、2026-10-31。Claude君も同意）。U4 から §4 の記録で確かめ始める。

### 5.3 分けて確かめる関係

| 仮説の関係 | 次に確かめること |
|---|---|
| 知識を蓄積すると、次の適用が容易になる | 同じ程度の課題で、調査の時間や手戻りが減るか |
| 自動化・専門の AI の参加で、処理の能力が上がる | 検証の品質を保ちながら、人間の実作業が減るか |
| 適用が容易になると、実用性が認められる | 初めての利用者が、自分の業務で使い、続けて使うか（1,000 回を待たずに小さく試せる） |
| 利用が広がると、経済の効率・持続可能性が高まる | 実際の判断と運用で、余剰の在庫・能力・廃棄などが減るか |

### 5.4 人と AI の役割の境界（設計の論点）

- 律速になりうるのは、コードを書くことより、**人の判断（段階 5）と誤りを見つけること（段階 7）**。段階 4・6 だけが速くなると、誤りも速く増える。先に自動化するのは、判断に要る材料をそろえること（比べる案・固定する条件・見込み）と、確認の仕組み（golden・読解試験・受入の条件）。
- 人が持つもの：目的、価値の基準、許容の範囲、重要な変更の採否。その範囲の中の定型的な Data・Parameter の変更は、将来 AI に判断と実行を任せ、新しい意味や例外が出たら人へ戻す設計が考えられる（GPT君の案）。
- 専門の AI（例：AI-Management-Consultant君、GPT-MC君）は、段階 1・2 で業務の目的を問い直し、仮定と比べる案を整える役。段階 5 の「選ぶ」は人が持つ（モデルの結果に責任を負えるのは人であり、実企業が採用するときの信頼の条件になる）。
- 担当が増えるほど、誰が案を作り、誰が何を確かめ、誰が採用したかの記録が効いてくる。

採否：提案（2026-10-31 の対話）。
