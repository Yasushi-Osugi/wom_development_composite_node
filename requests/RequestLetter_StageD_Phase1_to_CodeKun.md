## 0. 方針と決まったこと

### 0.1 方針

- **今の PPC を拡張して段階 D を作らない。** PPC は市場 leaf だけを起点にし、中間ノードの費用を leaf から逆算し、販売週に計上する（調査 §1）。設計の「LOVEM の実出荷と 1 対 1 の出荷記録」「費用を発生週で在庫原価に積む」と合わない。
- 段階 D は、**区間ごとの実出荷の記録を起点にした新しい台帳**として作る（新しいパッケージ `wom/valuechain/`）。計画の結果を読むだけで、計画を変えない。
- PPC は今のまま残し、台帳と並べて、どこが同じでどこがなぜ違うかを示す（設計 §8 の 9）。
- 区間ごとの出荷の記録は、後で World Map を実出荷で動かすときの `edge_flows`（区間 × 週 × lot 数）にも使う。その集計の関数を用意しておく（World Map 自体は今回作らない）。

### 0.3 supply point の扱い（大杉さん、2026-10-01）

- supply point は、inbound の木と outbound の木をつなぐ**仮想のノード**（グローバル需給センター、仮想の HQ 機能）である。物理の輸送・在庫・運賃を持たない。
- 台帳の物理の区間は、supply point を飛ばして結ぶ（例：`Factory_GP_CN → DC_Import_Buffer`）。
- 運賃のマスターにある `MOM->SP_…`・`SP_…->DC_…` の行（調査 §1.2 の 40 行）は、ノード費用の運賃を計画の木の区間に機械的に写したもので、**物理の区間の情報として使えない**（例：DC の「DC→ディーラー配送費」が、DC に入る区間 `SP->DC` に書かれている）。台帳はこれらの行を読まない。

## Part 1　Value Chain の台帳（`wom/valuechain/`）

### 1-1　題材

- iphone は Part 0-1 の単位の修正だけ。台帳の題材にしない。

### 1-2　新しいマスター（題材の 2 モデルのフォルダに置く）

同じ値を 2 か所に書かない（今回の運賃の二重表記と同じ落とし穴を作らない）。読み込みのときに、同じ区間の同じ種類の価格が 2 か所に書かれていたら、**エラーで止める**。

| ファイル | 内容 |
|---|---|
| `vc_config.csv`（key,value） | `hq_currency`（HQ の報告通貨）、`common_currency`（国際共通の評価通貨）、`report_start`（報告の開始週。無ければ warmup の後の計画開始週）、`holding_rate_weekly`（在庫の保有費用の週率。空欄なら「未設定」と表示し、0 として計算しない） |
| `vc_entity.csv` | `entity_id`、名前、種類（group / external_supplier / external_channel / external_customer）、機能通貨、連結範囲に入るか |
| `vc_node_assignment.csv` | `node_id`、`product_id`、`entity_id`、チャネルの種類（① own / ② external / ③ online、leaf_out だけ）、現地通貨（市場の leaf だけ）。設計 §7.1・§7.2 の表をそのまま入れる。**名前から自動で判定しない** |

価格の出どころは次のとおりにする（1 つの価格は 1 か所だけ）。

| 価格 | 出どころ |
|---|---|
| 最終市場の価格（①③の売上、②の消費者への販売の観測） | `ppc_market_price.csv` |
| 終端の MOM から次の物理の区間への価格 | `ppc_transfer_price_rule.csv`。区間の両端の法人で、法人間の価格か法人内の管理価格かを決める（Cookie：Factory_GP_CN → DC_Import_Buffer は法人間 18,000 JPY、Factory_DP_JP → DC_Local_JP は法人内 21,000 JPY。alloc：Bottling_Noda → FG_WH_Noda は法人内、原価加算 10%） |

| 法人内の区間で管理価格が無いもの | **原価で振り替える**（管理利益 0）。V1 の表示で「原価振替」と分かるようにする |
| 外部の供給者からの仕入 | `ppc_supplier_cost.csv` |
| 運賃・関税・ノード費用 | `ppc_edge_cost_rule.csv`・`ppc_tariff_rule.csv`・`ppc_node_cost_rule.csv`（Part 0 で直した後のもの） |

### 1-3　記録（設計 §2）

**出荷の記録**：区間ごとの実出荷 1 件ごとに 1 行。計画 ID、出荷イベント ID、Lot_ID、品目（完成品か、どの部材か）、出荷ノード、受け手（ノード、または外部の相手の ID。①③ の leaf の販売は消費者 `CONSUMER:<leaf>`）、物理の区間、出荷週・到着週・売上認識週（＝出荷週、D-2）、lot 数と物量（`lot 数 × cpu_size × bom_qty`、単位を明記）。

- 計画の結果（identity の実出荷）を読むだけで作る。計画のコードを変えずに作れない場合は、止めて報告する。

**金額の明細**：1 件の出荷から複数の明細（売上、売上原価、運賃、関税、法人間の消去など）。各明細は、元の出荷の記録（または在庫の記録）の ID、元の金額と取引通貨、換算に使った為替・週・方法、三つの役割の通貨での換算額を持つ。

**在庫の記録**：Lot_ID ごとに原価を持つ（identity では Lot_ID で個別に追える。FIFO などの仮定は要らない）。物の所在（ノード／輸送中）と、原価を持つ法人を別の項目にする。到着は所在の振替だけで、原価の新しい受け入れではない（設計 §2.3）。

**加工・組立の記録**：組立ノードで、同じ Lot_ID の部材の原価 ＋ 加工費 → 完成品の原価。振り替える週は、**完成品が組立ノードの P に入った週**（調査 §5。部材がそろった週ではない）。部材の在庫と完成品の在庫の両方に同じ原価を残さない。

### 1-4　費用の分け方（設計 D-3）

| 費用 | 扱い |
|---|---|
| 外部からの仕入、法人間の仕入 | 在庫原価（受け手の法人） |
| 運賃（グループの中の区間、グループに入る区間） | 在庫原価。**受け手の法人が負担**（出荷時に支配が移る前提。設計 §4 の F→D の運賃 5 と同じ） |
| 運賃（グループから外部へ販売する区間） | 売り手の法人の、その週の販売費 |
| 関税・保険（国境の区間） | 在庫原価（輸入する受け手の法人） |
| `conversion_cost`（加工・取扱・通関） | 在庫原価 |
| `warehouse_cost`（保管）、`sga_cost` | その週の費用 |
| 在庫の保有費用（D-5） | その週の費用。独立した項目。`holding_rate_weekly` が空欄なら計算せず「未設定」 |

この表は `wom/valuechain/` の中の 1 か所に置き、報告書に載せる。

- 取引条件（FOB・CIF など）で運賃の負担を売り手と買い手に分けることは、第 1 回では扱わない（区間の運賃はすべて上の表の規則で負担を決める）。

### 1-5　三つの視点（設計 §1）

- V1：全ノード・全区間。法人内の区間も、管理価格（無ければ原価振替）で売上・仕入を立てる。
- V2：法人別。法人内の管理売上・管理仕入を除く。法人の在庫原価は、取得原価 ＋ その法人で発生した在庫原価の費用（法人内の管理利益を含めない）。
- V3：連結範囲。法人間の売上・仕入を消す。**内部の未実現利益は消さない**（第 2 回）。表示は「内部の未実現利益の消去前」。
- ② の外部チャネル（設計 §3.3）：DC → leaf_out の出荷がグループの外部売上（卸価格）。leaf_out の実出荷は「外部チャネルの消費者への販売（観測）」で、グループの売上に足さない。leaf_out の在庫は「外部チャネルの在庫（観測）」で、グループの在庫に足さない。

### 1-6　為替（設計 §5、判断 d）

- 為替は `ppc_fx_rate.csv` だけを使う（モデルに無ければ `data/ppc` の見本。どちらを使ったかを記録する）。Landed Cost の `edge_cost_master.csv` の `fx_rate` は使わない。
- 2 つの通貨の間の換算は、基準通貨を経由して作る（例：EUR→USD ＝ EUR→基準 ÷ USD→基準）。これで同じ週の EUR→USD→JPY と EUR→JPY が一致する。
- 取引は、その取引の週の為替で換算する。在庫原価は取得時の換算額のまま払い出し、販売週に換算し直さない。法人間の取引は、売り手・買い手・消去で同じ出荷の記録の為替を使う。
- **表の最初の週より前（助走週）**：最初の週のレートを使い、使ったことを明細と `vc_fx_log.csv` に記録する（判断 d）。
- **表の最後の週より後、または通貨そのものが無い**：未評価（NaN）にして記録する。**黙って 1 にしない。前の週への退避もしない。**
- 合計の表示：未評価の明細があるときは、評価できた分の合計と、未評価の件数・lot 数を並べて出す。未評価を 0 として足さない。

### 1-7　warmup からの接続（設計 §6）

- 台帳は計画の最初の週（助走週を含む）から作る。報告の開始週（`report_start`）の期首の在庫原価は、助走週に積んだ在庫原価を引き継ぐ。
- 報告の期間の利益には、助走週に起きた売上・費用を含めない。期首の在庫原価として引き継いだ原価は、販売の週に売上原価として払い出す。

### 1-8　道具

- `python -m tools.valuechain_run --model-dir data\sample\<モデル> --out output\valuechain\<モデル>\run_1 [--lovem-run <LOVEM の run フォルダ>]`
- 出力：出荷の記録、金額の明細、在庫の記録（週末の残高）、V1・V2・V3 の週ごと（単週と累計）の表、`vc_missing_prices.csv`、`vc_fx_log.csv`、PPC との対応表（§8 の 9）。CSV で出す。
- `--lovem-run` を付けたときは、受入条件 2 の照合を行い、結果を出力に入れる。

## Part 2　表示（Management の中の「Value Chain」）
