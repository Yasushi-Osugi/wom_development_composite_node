## 0. この実験の目的と読み方

### 0.1 目的

目的は化粧品のモデルを完成させることではない。BS-SEAF の手順（Self-Evolving Modeling Loop の 8 段階）が、**お米とは別の業務に使えるか**を確かめる。

- お米で残した知識（決定記録、Start Here、報告書）を、どこで再利用できたか。
- 新しい業務の意味のうち、どれをデータ・パラメータで表せ、どれが構造の話になるか。
- 各段階の判断が、根拠と検証結果まで追えるか。

### 0.2 記述の区分（Sol君の案）

| 印 | 区分 | 条件 |
|---|---|---|
| **[事実]** | 確認済みの事実 | 出典と確認日がある |
| **[仮定]** | 実験用の仮定 | 実験のために置いた値・前提。現実の値ではない |
| **[方針]** | 人間が決める方針 | 大杉さんが決める（§6 に記録） |
| **[未確認]** | 未確認事項 | 追加の調査や判断が要る |

### 0.3 対応状況の 3 段階（第3段階で使う）

| 印 | 意味 |
|---|---|
| **守れる** | 計画に反映され、計画そのものが条件を守る |
| **検出** | 計画は条件を守らないが、結果から違反を見つけられる |
| **未確認** | 対応できるかどうか、まだ確かめていない |

対応の手段は **Data／Parameter／Core** で記録する（Self-Evolving Modeling Loop の「変更方法の選択」）。v0.1 は「基準ケースは Core の変更ゼロ」を目標にした。v0.2 では、大杉さんの判断で**歩留まりを Core に入れる**（§6 D1、§7）。これは BS-SEAF のループで「データでも表せるが、意味を一つの数に混ぜないために構造を変える」と判断した、最初の事例として記録する（§3.2）。

## 2. 第2段階：業務の意味モデル

### 2.1 自然言語の説明（出発点）

- 日本の工場で美容液とクリームを作る（調合・充填・包装）。
- 作った製品のうち、完成品の出荷時点の歩留まりの分だけが良品として出荷できる。
- 良品は品質確認（出荷判定）を終えてから出荷できる。
- 判定を終えた製品を海上輸送でシンガポールの DC へ送り、直営店・公式 EC・代理店へ届ける。
- 直営店は開店週より前には売らない。開店時の店頭在庫は、計画の中の先行生産で用意する。
- 納品時には、使用期限まで一定の期間が残っていなければならない。
- 正規の販路にだけ供給し、値引きはしない。
- 工場には週ごとの物理の能力の上限（設備）と、生産操業計画（シフト）の能力がある。

### 2.2 概念と関係

```
原料（日本で調達）
  └→ 日本の工場：調合・充填・包装
       （投入の能力：Sealing_Qty＝cap_hard、Production_Qty＝cap_soft。歩留まり y）
       （引当て可能な完成品＝能力 × y）
       └→ 品質確認（判定の期間）
            └→ 判定済み倉庫（日本、輸出前）
                 └→ 海上輸送
                      └→ シンガポールの DC
                           ├→ 直営店（① 自社、開店週あり）
                           ├→ 公式 EC（③ 自社ネット）
                           └→ 代理店（② 外部の法人、sell-in）
需要：SKU × チャネル × 週（lot）。Lot_ID は需要週を持つ
法人：日本本社（JPY）／シンガポール販社（SGD）／代理店（外部）
```

### 3.2 中心の差分 2 件（大杉さんの判断で決着）

#### COS-R04／R13：品質

- **二つに分けた**：品質確認の「期間」は区間の時間（COS-R04、Data）、不良の「量」は完成品の出荷時点の歩留まり（COS-R13、Core）。
- **歩留まりの考え方（大杉さん）**：ある週について、
  - 設備の物理的な能力の上限＝Capacity Hard＝**Sealing_Qty**
  - 生産操業計画（人のシフト体制）＝Capacity Soft＝**Production_Qty**
  - 当週の出荷量（＝当週の引当て可能な製品数）：**Ship_Qty ＝ Production_Qty × yield rate**
  - 不良がどの工程で起きたかは見ず、完成品の出荷時点に一本化した歩留まりを、当初の生産投入の計画に対する製造品質の実力として使う。
  - 「歩留まりを考慮した完成品の引当て可能出荷数量」を「当週の生産計画 LOT 数」として扱う。
- **Lot_ID との整合**：不良の分の Lot_ID は作らない（作って消すと、数量の保存と Lot_ID の同一性が崩れる）。Lot_ID はすべて良品の完成品であり、不良は「投入の物量が lot の数より多い」こととして物量の解釈で表す（`bom_qty` と同じ考え方。§7.3）。
- **データだけで表す案を採らなかった理由（Semantic Gap Analysis の記録）**：`capacity_plan.csv` の能力にあらかじめ歩留まりを掛けておけば、Core を変えずに同じ計画になる。しかしそうすると、CSV の能力が「設備の物理の能力」と「製造品質の実力」を混ぜた一つの数になり、PSI のグラフの能力の線も物理の能力でなくなる（誤読の落とし穴）。また歩留まりが数として残らず、変更課題や金額（良品 1 lot 当たりの原価）で使えない。**意味を分けたまま持つために、構造を変える**（Meaning First, Structure When Necessary）。
- **限界**：工程別の不良、週ごとに変わる歩留まり、判定の結果で出荷を止める判断は扱わない。

#### COS-R05：納品時の残存期間

- **判定（大杉さんの第一感を採用）**：ある Lot_ID について、
  - **工場の出荷週** `w_ship`：工場（MOM）でその Lot_ID が実際に出荷された週（Forward の実出荷 `_actual_ship`）。
  - **市場の納品週** `w_due`：その Lot_ID の需要週（`LotIDGenerator.parse()` で読む）。遅配の lot は、需要週の代わりに市場での実出荷週（`w_due = max(需要週, 市場の実出荷週)`）。
  - **判定**：`w_due − w_ship ≦ 52 週`（A5・A6 から）。超えた lot を一覧にする。
- 遅配の lot に `max` を使うのは、遅配の lot では需要週で測ると滞留を実際より短く数えるため。ただし遅配の lot は工場の出荷が遅れたものなので、実際には上限を超えにくい。
- **週の差は計画の週の番号で数える**。ISO の週ラベルの引き算はしない（§2.4）。
- 起点は工場の出荷週であり、製造日そのものではない。基準ケースの工場は pull の MOM で、作った週に出荷するので、差は無い（push のバッファの MOM で使うときは、工場の中の滞留を数えない点に注意）。
- **Capacity Layer は使わない**（v0.1 の案を取り下げた）。判定は Core を変えない道具で足りる。計画が上限を守るように作るわけではないので、対応状況は「検出」。違反が出たときの原因の候補は、能力不足による Backward の前倒し（上限が無い。Start Here §7）、warmup・安全在庫の積み過ぎ。そのときの手当て（能力・Capacity Layer など）は、違反が出てから考える。

## 7. 歩留まりの Core 実装の設計（依頼書の前提）

### 7.1 属性

- `sc_tree_master.csv` に列 `yield_rate` を足す（MOM の行に書く）。`PlanNode.yield_rate`（既定 1.0）。
- 列が無い・空欄＝1.0（不良なし。今のモデルの意味のまま）。`bom_qty` の空欄＝1 と同じ扱い。
- 0 以下・1 を超える・数値でない値は、読み込みで止める（ファイル・行・値を出す）。
- **MOM 以外のノードに書いたら止める**（完成品の出荷時点に一本化する。D1）。
- 週ごとの変化は扱わない（ノード × 製品で一定）。

### 7.2 能力の意味

- `capacity_plan.csv` の `max_supply`（cap_hard＝Sealing_Qty）と `cap_soft`（Production_Qty）は、**今までどおり物理の投入の能力**（lot 換算）。CSV の意味は変えない。
- エンジンが lot を置く・封じるときの上限は、**引当て可能な完成品の lot 数＝floor（能力 × `yield_rate`）**。
- 端数は切り捨てる（作れない分を作れたことにしない）。
- 能力ゼロ（0）・未設定（空欄）・休業の意味は変えない（0 × y＝0、未設定は未設定のまま）。
- 操業カレンダーから cap_soft を導く処理（`capacity_sealer.py`、shift × cap_hard ÷ 21）は物理の能力を作るので、そのまま。歩留まりはその後に掛ける。

### 7.3 Lot_ID と物量

- lot のリストは変えない。lot はすべて良品の完成品。
- 投入の物量（原料・工場の処理量）の解釈だけを `1 / yield_rate` 倍にする（`bom_qty` と同じく、エンジンの外の解釈）。良品 1 lot 当たりの原料・加工の原価が `1 / yield_rate` 倍になるのも、この解釈から出る。
- 金額（PPC・Value Chain）への反映は、**依頼書を分ける**（Part A：計画、Part B：金額）。Part A では数量だけを扱う。

### 7.4 変える場所（2026-10-25 の調査。Q4 で漏れを確かめる）

能力を使っている箇所は次のとおりで、歩留まりはここだけに入れればよい見込み。

| ファイル | 箇所 | 中身 |
|---|---|---|
| `wom/model/plan_node.py` | `cap_hard()`・`cap_soft()`・`processing_limit()` | 能力の読み出し。**引当て可能な完成品の上限を返す読み出しを 1 つ足し、エンジンはそれを使う**（`cap_hard()`・`cap_soft()` は物理の値のまま残す。名前は依頼書で決める） |
| `wom/engine/backward_planner.py` | `_apply_mom_cap_backward`（520・530 行付近） | MOM の能力での切り詰めと前週への押し戻し |
| `wom/engine/forward_planner.py` | Step 0a（702 行付近）、Kitting Gate（975 行付近） | 能力での封印、組立の成立 |
| `wom/engine/capacity_sealer.py` | 250 行付近 | 封印の記録 |
| `wom/capacity_layer/serial_adapter.py` | `processing_limit` の取り込み | 上位の層（既定 OFF） |

`plan_node.py`・`backward_planner.py`・`forward_planner.py` は**保護対象のコア**なので、依頼書・3 層のテスト・大杉さんの diff 確認が要る（`AGENTS.md` §10）。

### 7.5 テスト

- **Unit**：歩留まり 0.97・能力 100 の MOM で、週の良品 lot が 97 を超えない（Backward・Forward の両方）。
- **Integration**：`sc_tree_master.csv` の列 → ローダ → ノードの経路（cap_soft・`init_stock_days` の休眠と同じ型の事故を防ぐ）。不正な値・MOM 以外への記入で止まる。
- **E2E golden**：どのモデルも列を持たないので、全 golden が不変（V10）。歩留まり 1.0 を明示したモデルも、列が無い場合と完全に一致する。

### 7.6 画面の注意（申し送り）

PSI のグラフの能力の線は物理の能力（cap_hard・cap_soft）のまま描かれる。歩留まりのある MOM では、P（良品の lot）が能力の線より常に下になる。誤読を防ぐため、引当て可能な上限（能力 × 歩留まり）の線を足すかは、Part A の後に決める。
