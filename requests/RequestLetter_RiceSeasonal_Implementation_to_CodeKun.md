## 0. 目的と正典

将来の市場需要IDを過去の実行可能な収穫に割り当て、玄米保管拠点へ運び、需要に近い週に精米して供給する。
市場のLot_ID・要求週を保ち、数量と物量の根拠をLOVEM / World Map / 将来のValue Chainへ返す。

最初にAGENTS.md、docs/WOM_Start_Here.md、LotID決定記録、設計・検証報告を読む。
既存serial_adapterの一つの内部計画週をそのまま流用せず、収穫h・精米pの二つの週を持つ。
今回の基準を取り違えず、着手SHAと差分を報告する。

### B — 上位層の独立したRiceアダプター・プラグイン

新規のRiceアダプターと専用プラグイン（既定OFF）に一般化する。既存serialのOFF/ON・smartx計画・goldenを変えない。

1. 通常のlot_generatorで作られた市場Sから、ID・要求週・品目・チャネルを取得する。
2. h/pの候補を作り、週の収穫能力・年産収穫量・集荷/倉庫受入れ・玄米保管・精米・DC/市場の資源を予約する。
3. 品目をまたぐ設備は明示したresource_idで**一度の共同問題**として解く。品目別に同じ共有能力を使い切らない。
4. 整数ID割当数→精米の前倒し→玄米kg週の順に解く。既存LPの連続上界と整数結果を分ける。分数IDは出荷しない。
5. 元のIDで内部S/Pだけを配置する。未割当IDは元の市場要求に残し、消したり別週の新IDに置き換えたりしない。
6. Forward identityの実出荷・I・COと照合する。計画上の割当と実出荷を別々に報告する。

**規模の注意**: 試作は1IDごとの候補変数を使う。通常Riceでは同一の品目/経路/要求週/物量条件を集約し、
整数割当数量を解いてから元IDの順序で展開する。最終需要IDの消失/重複が無いことを照合する。
集約してよい条件が違うlotを一緒にしない。全モデルを1IDごとの巨大MILPで走らせる前に、
候補数・非ゼロ係数数・メモリ・実行時間を測る。サンプル全量の性能は今回の試作では未検証。

**フックの注意**: 現行GUI/headlessは品目ごとにBackward→hook→copy→Forwardを完了してから次の品目へ進む。
共有資源を解く場合、全品目の市場需要・能力を確定した時点で共同計算し、各品目のPOST_BACKWARDではその品目の内部位置だけを渡す。
PRE_PLANの市場需要変更プラグイン（Holiday等）の**後**に計算する順序を保証する。後の品目のBackwardで配置が上書きされる構成にしない。
フック順序で保証できなければ、GUI/headlessの呼び出し層で共同計算点を明示し、既存方式への影響をテストする。

### C — 通常Riceの移行用コピーで検証

元Riceはlegacyの比較用として保持し、新しい移行用コピーで両品目・全市場を確認する。
HarvestBatchを使わず、収穫時点から将来需要IDが付いた供給を形成する。
過年度需要を増やして年産能力を消費する処理と、将来需要の先行収穫割当は別に持つ。
報告期首在庫は先行収穫の履歴から求める。OI_の生成、anonymous binding、無根拠の需要の上積みをしない。
元モデルとgoldenの置換は、移行用コピーの受入・Ownerの差分確認の後。

## 2. 入力の設計対象

名前は案。実装では最少のCSV群にまとめてもよいが、次の意味を失わない。

| 入力 | 必須の意味・キー |
|---|---|
| 需要/経路 | product・market・元lot_id・元due_week、田/集荷/仮想SP/玄米倉庫/精米/DC/市場、LT |
| 品目のレシピ | 精米kg/需要lot、歩留まり、その他の産出。米の品種と玄米/精米のstageを区別 |
| 資源割当 | node/product/stage→resource_id。資源単位を明示。共有する設備を名前から推測しない |
| 物理的な上限 | 設備のCapHard。使用量のkg/需要lot換算を根拠付きで保持。カレンダーで値を破壊しない |
| 収穫カレンダー | resource_id・ISO週・crop_season・その週の供給可能量。非収穫週は候補外/可能量0 |
| 年産上限 | resource_id・crop_season・収穫可能な玄米kg。週設備能力の単純な合計とは独立 |
| 保管/工程能力 | 資源×週、玄米kg/週・精米kg/週と倉庫kgを区別。None/0/欠落を混ぜない |
| 方針 | 収穫遡及窓、玄米最大保存期間、精米前倒し許容、優先順位、report_start |

倉庫の期末Iは[a,b)。容量は週内の前週末I＋P、払出し前の保守的なピーク[a,b]で検査する。
玄米倉庫を出た後に精米へ届くまでの物は輸送中。在庫から消して「存在しない物」として扱わない。
加工時に玄米を消費し、精米とその他の産出へ変換する。玄米と精米に同じ原価を二重に残さない。
今回は副産物の売上・廃棄費・金額台帳への接続を実装範囲へ追加しない。物量を記録し次の設計へ渡す。

## 3. 単位・能力・表示

- 現行headless Planningは需要CSVのquantityをlot数としてID生成（cpu_size=1）する。cpu_sizeの物量換算を理由に、ID数をもう一度割らない。今回の検算CSVも1 lot、設定cpu_size=10。
- 通常Riceの現行uom=lot、cpu_size=1にはkgの対応が確定していない。数量の意味を壊して同じ数値をkgと呼ばない。
- 物理上限、季節の供給可能量、休業を別の属性にする。0.1の整数化に依存しない。元CapHardを季節状態の特殊値で上書きしない。
- 非収穫週P=0、原IDの保管、精米成立週、残る不足IDを表示・出力する。
- LOVEMは需要lot相当のIと段階別物量を区別する。World Mapは実出荷だけを描く。新たな金額を仮価格で捏造しない。

## 8. Claude君の補足（2026-10-08、レビュー時に追記）

Sol君の試作を基準 26a1e8e で再実行した。試作22件と既存69件を**一回の実行で91 passed**、probe の3条件の結果も報告と一致。止める理由はない。
通常 Rice のデータを見て、C の前に効く事実を4つ書いておく。

1. **コシヒカリは年産の収穫能力が需要より少ない。** 現行 `capacity_plan.csv` の収穫は年 46,500 lot（W41〜W43 の3週）、需要は年 59,903 lot。約22%足りない。ゆめぴりかは 18,200 対 17,940 でほぼ釣り合う。legacy ではこの不足が市場に見えていなかった。identity に移すと、市場に注文残として出るのが正しい結果。
2. **保管と遡及の窓は年単位になる。** 収穫は年1回なので、翌年の収穫直前の需要は約1年前の収穫から来る。試作の 13週／10週（`scenario.json` の policy）では通常 Rice は解けない。窓の値は §7 で決める。
3. **2026 年は助走の年になる。** 需要は 2026-W01 から始まるが、2025 年産の収穫は計画期間の外。2026-W01〜収穫到着前の需要は供給が無く、注文残になる。報告の開始（`report_start`）と、助走期間の注文残を別に数える。匿名の期首在庫で埋めない。
4. **精米センター東・西は品目の共用設備**（`node_master.csv` の説明）。今の能力表は品目ごとの値。共同の resource_id にするときの設備能力の値は §7 で決める。

その他：
- `tools/probe_rice_seasonal_definition.py` は HEAD が 26a1e8e のときしか動かない。A で、記録の再現用の SHA 照合は残したまま、現在の HEAD でも測れる起動の仕方（例 `--allow-head`）を足してよい。
- C の値（§7）は Owner の決定を待つ。A と B は値に依存しないので先に進めてよい。決まった値はこの節の下に追記してから C に入る。
