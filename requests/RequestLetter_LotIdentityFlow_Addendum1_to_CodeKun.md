## A1　K4（CO の重複）：原因を確かめ、identity でだけ直す

### 事実（中間報告）

- CO の中で同じ Lot_ID が重複する。legacy でも smartphone 60,333、smartx 220,452、ev_update 4,632、rice 451,309 件ある。identity では rice だけが 9,029,146 件（約20倍）に増える。
- 推定原因は Step 0a（cap_hard の封印）である。cap_hard を超えた P の lot を `CO[w+1]` に入れている（`forward_planner.py` の Step 0a）。

### Claude君のコードの読み

- Step 0a は、作れなかった**生産の lot（供給側）**を、**要求（CO、需要側）**に入れている。ところが、その lot の要求はすでに S にある。このため、同じ ID の要求が2件になる。
- CO の要求は、供給（I＋P）と照合したときにしか消えない。一方、封印された lot は P から消されたまま、二度と生産されない。したがって、この CO は永久に残る。
- Explicit Closure の E2（休業週の P は、ID を保ったまま次の開いている週の P へ送る）のコメントにも、「Step 0a would drop the lots from the supply side」とある。つまり、Step 0a が lot を供給から落とすことは、すでに知られていた。

### 依頼

1. まず `k4_probe.py` で、上の推定が正しいかを確かめる。モデルごとに、重複の何割が Step 0a に由来するかを示す。
2. 推定が正しければ、**identity でだけ**、Step 0a を次のように変える（legacy は変えない。legacy の重複は既知の欠陥として報告書に記録するだけにする）。
   - cap_hard を超えた P の lot は、CO に入れない。**ID を保ったまま、翌週の P の先頭に回す**（前の週から持ち越した lot を、新しい lot より先に作る）。
   - 休業週は、E2 と同じく、次の開いている週まで送る。
   - 計画期間の終わりを越えた分は、`closure_p_unplaced` と同じ形で記録する（黙って捨てない）。
   - 業務上の意味：能力を超えた分は、作れる週まで生産がずれる。要求が二重になることはない。**生産がずれても、そのノードの要求週（S の週）に間に合えば遅配ではない。** 遅配になるのは、要求週より後に出荷した場合だけである。
   - 複数の週から持ち越した lot の順序（古い週の lot が先）が逆転しないことを、ユニットテストで確かめる。
3. E2 が送った lot を next open week の P の末尾に置いている件は、identity で先頭と末尾のどちらが正しいかを確かめて報告する。identity の Step 0a を「先頭」にすることで、E2 の lot と順序が食い違うなら、そちらも identity でだけ「先頭」にそろえる。
4. 直した後に、K4 を全 16 ケースで取り直す。K4 と rice の市場実績を、修正前と修正後で比べる。
5. Step 0a の対象を確かめる。Step 0a は、push 以外で cap_hard が正のノードすべての P に効く。モデルごとに、封印が実際に起きたノードを node_type 別に数える。
   - P が生産を表すノード（MOM など）：上の 2 のとおり、生産の繰り延べである。
   - P が調達・輸送による入庫を表すノード（leaf_in、DAD など）：翌週へ回すのは「入庫の処理待ち」であり、生産の延期ではない。動きは同じ実装でよいが、報告書では件数を分けて示す。
   - Kitting の組立ノード：Kitting Gate が能力を部材の払出の前に適用しているので、Step 0a は起きないはずである。起きていれば、部材の払出・消費と完成品の P の対応が崩れていないかを確かめて報告する。

## A2　rice：当面は legacy で動かす

- rice の HarvestBatch は、需要に紐づかない合成 ID（`OI_…`）で収穫在庫を作る。この ID は Lot_ID の照合で、どの需要とも一致しない。そのため identity では、市場実績が 235,316 から 35,266 に崩れる（中間報告）。
- これは決定記録 §6（Buffering Stock、rice の合成 ID）の未決事項そのものである。収穫在庫に需要の Lot_ID を付ける設計が決まるまで、**rice は `lot_flow_mode=legacy` で動かす**。
  - rice の `planning_config.csv` に `lot_flow_mode,legacy` を加える（ファイルが無ければ、既存のモデルの書式に合わせて作る）。
  - rice の golden は legacy のままなので、変わらないことを確かめる。
- ただし、identity での rice の結果（A1 の修正の後）は、原因の切り分けとともに報告書に残す。「OI_ の照合不能による分」と「K4 による分」をそれぞれ示す。
- これは従来の動きを保つための暫定措置であり、rice の供給と金額の整合性を確かめたものではない。**どの方式で動かしたかを、計画の結果（ForwardPlanResult など）と LOVEM の manifest に記録する**。報告書にも、rice は identity の対象外であると明記する。

## A3　decouple の配置最適化：legacy で参考候補を選び、identity で評価し直す

- identity では、デカップリング点をどこに置いても計画が変わらず、配置の候補を区別できなくなった（中間報告）。これは、**今の実装では**配置の効果が「下流の P を需要 P のコピーで作ること（例外2）」だけに依存していたことを示す。
- デカップリング点の本来の意味（補充の指示、在庫の目標、投入の時期を変えること）まで失われたわけではない。identity でのデカップリング点の意味は、別途設計する（決定記録 §6 に追加）。
- 当面は次のように扱う。
  - decouple の配置最適化と BufferingStockOptimizerPlugin は、実行時の方式によらず、**legacy で参考候補を選ぶ**。
  - 選んだ配置を、その run の方式（既定 identity）で**評価し直し**、その結果で本計画を行う。
  - legacy の評価値を、identity で実現できる成果や、最適であることの証明として扱わない。画面や出力で legacy の評価値を示す場合は、「legacy による参考値」と分かるようにする。
- 中間報告で legacy に固定した 4 件のテストは、この方針で説明がつく。ev-europe の在庫置場のテスト（売上基準値の変化）は、legacy に固定したまま、identity での値を報告書に記す。

## A4　報告書に加えるもの

- `ot_unrouted`（子が複数ある親から出荷され、どの子にも振り分けられなかった lot）の件数を、モデルごとに示す。0 でなければ、ノード・週・ID の例を示す。
- ev-thailand で「立ち上がり期の 400 件が全期間 CO に残る」件は、今回は直さない。原因を断定せずに、該当するノード・週について、要求週・必要な生産週・実際の供給の履歴を示す。計画期間の開始前に作るべきだった分であることが確かめられれば、決定記録 §4（期首在庫を warmup で作る）で扱う。
- identity で期末注文残が出るモデル（smartphone 99,064 など）ごとに、その原因を件数の多い順に上位3つまで示す。原因の分類は、能力（cap_hard）・休業・ID の照合不能・経路の未割当（`ot_unrouted`）・計画期間の端とする。どれにも当てはまらないものは「未確認」として件数を残す。大杉さんが `python -m main` で確かめる画面の案内にも使う。
- PPC については、「市場の実出荷が金額に届くようになった」範囲で報告する。中間ノードの金額（各ノードの実出荷に対応する売上・原価・利益）は今回の範囲外である（本体 C4）。

## 改訂の要点（v1.1、Astra君のレビューを反映）

実装中の場合は、ここだけ読めば差分が分かる。

1. **A1**：生産がずれても、そのノードの要求週に間に合えば遅配ではない。持ち越した lot の順序のテストを追加する。Step 0a の対象を node_type 別に数え、生産の繰り延べと入庫の処理待ちを分けて報告する。Kitting の組立ノードで Step 0a が起きないことを確かめる（A1 の 2・5）。
2. **A2**：どの方式で動かしたかを、計画の結果と LOVEM の manifest に記録する。rice は identity の対象外であると報告書に明記する。
3. **A3**：legacy は参考候補を選ぶためだけに使い、選んだ配置を identity で評価し直して本計画を行う。legacy の評価値を identity の成果として扱わない。「今の実装では、配置の効果が例外2に依存していた」と記述する（「当然の帰結」とは書かない）。
4. **A4**：原因を断定しない。期末注文残の原因は 5 分類＋未確認で示す。PPC は市場の範囲で報告する。
